## 1. 改造前：结构上为什么不可能"你来我往"

**【事实】** 对话的唯一入口是"决策 → 单条措辞 → 一条事件"：每个 agent 在满足触发条件时被要求"用一句话自然地说点什么"，LLM 返回一句话，即成为一条独立 `MSG_*` 事件（`code/life/agent.py:729-767`、`code/orchestration/integration.py:739-841`）。

**【事实】** 消息层**没有会话对象**：`reply_to` / `in_reply_to` / `thread_id` 在代码与文档中无定义；`MSG_PUBLIC.payload.topic` 键存在但恒为空；`refs`（唯一可能的"指向另一条消息"通道）恒为空数组（同上）。

**【事实】** 生成时看不见对方上一句：提示词只含「人设压缩档案 + 场景模板 id + 对象名 + 一句指令」，不含最近对话、对方上一句、关系亲密度、情绪、地点、时间（`code/life/agent.py` 的 `_dialogue_prompt`）。

**【事实】** 触发有四道门（缺一不说）：社会声道总开关、LLM 档位许可、**每个 agent 每个时段最多一次**、**计划里该时段必须带场景模板**（`code/life/agent.py:735-746` 及其上下文）。

**【判断】** 第三条门很关键：**"每个时段最多一次"本身就限制了一条对话不可能在同一个人身上连续发生两轮**。所以即便提示词写得再好，结构上也出不了多轮——这也是为什么本轮把"线程化"当靶心，而不是继续调措辞。真实世界里的对话，恰恰是同一个时段里你来我往的几轮。

> **更新约定（追加式，不覆盖）**：本断言按时间序列维护——若日后复跑结果为空，**追加新的时刻与 HEAD sha 与空结果，保留旧的时刻**；若某次不为空，同样追加该次记录并说明是哪次改动导致。**不得用新结果覆盖旧记录**，否则读者无法判断哪一句对应哪一版代码。

> **`meta.json` sha 登记（会被重生成，引用须现算）**：A0 `meta.json` 现为 **`5fe058f3`**（此前一轮为 `392748a2`，跑后重生成过，原因含补写字段）；v0-anchor `meta.json` 为 **`165c002a`**。两臂 `run.jsonl` 未变（`643f13a5` / `c1f86bf6`）。**引用 meta 时一律现算 sha，不写记忆值**——元数据文件比日志更容易被事后补写。

> 填表纪律：`code_sha` 与 `run.jsonl` sha 一律从该臂 `meta.json` 读取后填入，**不得填 `git rev-parse HEAD` 的当前值**；填表时重新 `sha256sum` 校验一次，防止沿用骨架旧值。
>
> **注意**：`prompt_sha(v0-anchor)` 与 `prompt_sha(A0)` **本就不同**（A0 含显示名/称谓注入与 `_reply_prompt` 承接装配等必要适配），差异须能逐项归因；能归因即正常对照，不叫「作废」。


**【事实】** 改造只在对话路径上做**受控解冻**（范围与四条前提见 R1 §5），方式是**只追加字段、不新增事件类型**：在 `MSG_DM` / `MSG_PUBLIC` / `MSG_GROUP` 的 payload 上增加线程字段——`thread_id`、`turn_index`、`reply_to`、`participants`、`ctx`（关系/情绪/需求/话题）。

**【事实】** `thread_id` 在生成侧保证全局唯一，按渠道区分：
- 定向私信：`TH-<发起人>-<对方>-<发起回合>`
- 群组：`TH-<发起人>-G<群 id>-<发起回合>`
- 公开：`TH-<发起人>-PUB-<发起回合>-<k>`（k 为该 agent 该回合内公开消息的自增序号）

**【判断】** 唯一性不是为了好看，而是**为了能被正确分组**。曾经的设计只用「发起人 + 回合」，同一人在同一回合向两个不同对象各发一条私信就会撞号；按 `thread_id` 分组会把两条独立对话并成一条，平均轮次、最长轮次、重复率**全部失真**。对端进 id 之后这个坑才被补上。

**【事实】** 线程边界规则（**只约束生成，不参与复算**）：
- 开始：某 agent 发起一条消息，且当前时段内与同一对象没有"未回应的入站消息" ⇒ 新建线程，`turn_index = 0`，`reply_to = null`；
- 延续：对线程内某条消息作答 ⇒ 沿用同一 `thread_id`，`turn_index = 已有最大值 + 1`，`reply_to = 被回复消息的 msg_id`；可跨回合延续（同时段内最远若干回合）；
- 结束：达到单线程最大轮次上限 / 末条之后若干回合无人回应 / 参与者离开场所 / 时段切换。

**【未完成】** 线程字段契约、上限阈值、回退开关的最终值以 D2 交付文档为准；本报告在 D2 定稿后回填确切数值与开关名，不复述未核实的部分。

## 3. 复算规则（读者按此重算，必得同一结果）

**【事实】** 改造后（`thread_schema = explicit`）：按 `thread_id` 分组，组内按 `(round, seq)` 升序排序即得一条线程；线程轮次 = 组内条数。

**【事实 · 指针解析判据】** `reply_to` 存的是 **`msg_uid`**（全局唯一键，格式 `<seed>:<预测全局seq>`），不是 `msg_id`——代码取值为 `p.get("msg_uid") or p.get("msg_id")`，优先唯一键。因此：
- `ptr_ok` = `reply_to` 能解析到**同 `thread_id` 且 `seq` 更早**的 `msg_uid`；
- `ptr_dangling` = 解析不到；`ptr_cross_thread` = 解析到别的线程；`ptr_forward` = 指向更晚的 `seq`；
- `msg_uid` 的唯一性由 `tools/d2/thread_metrics.py` 的 `msg_uid_unique` 断言给出（跑批时附读数）。

**【事实】** 旧格式日志（v0-anchor）没有 `msg_uid`、也没有线程字段，故 **不会出现"用 `msg_id` 当指针"的情况**——v0 的指针完整率恒为 0 是**字段缺失**，不是"发消息却都不回复"。

**【事实】** 改造前（`thread_schema = legacy`）：`thread_key = (day, channel, frozenset{from, to})`，同样按 `(round, seq)` 升序。

**【判断】** 把"边界规则"和"复算规则"分开是本设计的要点：边界规则只影响**新生成的世界**；复算规则对所有日志一致。这样将来若调整边界规则（例如把最大轮次从 6 改到 8），旧日志的线程切分数字**不会**跟着变——读者任何时候重算都得到与报告一致的结果。

**【判断】** 也正因为有这套规则，"改造前"也能算出一个线程数（212）——但那 212 条里 91.51% 只有一条消息。**这个数字是切分规则的产物，不是对话行为的产物**（见 §5.2）。

## 4. 指标与判定方式

**【事实】** 结构层的统计单位是 **per-thread**，不是 per-message；禁止把 per-message 均值冒充 per-thread。

| 编号 | 指标 | 定义式 |
|---|---|---|
| S-1 A | 交替轮次（**主口径**） | `turns_A = 1 + #{i : speaker(m_i) ≠ speaker(m_{i-1})}`，不依赖 `reply_to`，前后两臂都能算 |
| S-1 B | 往复对数（**仅后臂**） | `reply_to` 非空且指向同线程内他人消息的消息数；改造前无该字段，报 0 并标"字段缺失，非缺陷" |
| S-2 | 线程规模分布 | `|thread|` 的 p10/p50/p90/max |
| S-2 | 单条线程占比 / 独白线程占比 / 多轮线程占比 | 分母均为**线程数**；**长度 1 的线程不剔除、进入分母** |
| S-3 | 最长链 | 线程内最长连续交替段的条数 |
| S-4 | 指针完整率 | 分母 = 线程内非首条消息；分子 = `reply_to` 非空且指向同线程前序消息；分列 `ptr_empty` / `ptr_cross_thread` / `ptr_forward` / `ptr_ok` |
| S-5 | 孤儿消息率 | 无 `thread_id` 的消息数 / 消息总数（改造前 = 1.0，标 `legacy`） |

**【事实】** 判定方式（三条硬约束，来自 R1 §2.5 与全族纪律）：
1. **线程类指标不做显著性检验**——两臂分母天然不对称（改造前多轮线程 0，改造后几十个），做检验没有意义；
2. 两臂恒 0 / 恒 1 时 B2 退化为 0 **不是零噪声**，改用精确二项上界（0 事件时 95% 上界 ≈ 3/n），表中 `band_source` 列写 `rule-of-three(3/n)`；
3. 每张表必带 `band_source` 列（`B2(m=…)` / `rule-of-three(3/n)` / `无可用带`）与分母。

### 5.1c `max_turns` 2/4/6 三档 mock 对照（尾部受钳制、中位数不受；抬上限有反作用）

**【事实】** 同 seed / n / rounds（16 × 84 × 42）、同树连续跑，唯一变量 `--override life_v2.dialogue.max_turns=N`；provider = **mock**（零成本，7 分钟可逐字节复现）。证据：`v2/evidence/d2_maxturns_sweep_n16r84_seed42.md` (d5acad7c) + `.json` (511ec503)。

| `max_turns` | **p50** | **p90** | **max** | 多轮线程占比（≥3 轮） | 单发线程占比 |
|---|---|---|---|---|---|
| 2 | **2** | **2** | 2 | 0.0% | 42.8% |
| 4 | **1** | **4** | 4 | **38.2%** | 51.9% |
| 6 | **1** | **6** | 6 | **35.5%** | 56.1% |

**【判断 · 两句话（缺一不可）】**
1. **尾部受配置钳制、中位数不受**：`p90` **逐档跟随上限**（2→4→6），而 `p50` **卡在 1–2** ⇒ **想让普通一次搭话聊到 3 轮以上，只抬 `max_turns` 无效**。
2. **抬上限有反作用**：`≥3 轮占比` 在 **mt=4 就饱和（38.2%）**、**mt=6 反降到 35.5%**，同时**单发线程升到 56.1%** ⇒ 线程变长**挤压了新起线程**；真正要动的是**触发/承接机制**（谁先开口、何时接话、单 slot 消息上限），属 **D2.1**。

**【事实 · 按预登记判据的判定】** 用 §6 预设判据（继续增长＝`p50` 单调上升且 `p90` 至少提一档；早收敛＝`p50` 差 ≤1 且 `p90` 不变）：`p50` 不单调（2→1→1）⇒ 「继续增长」不成立；`p90` 跟随上限 ⇒ 「早收敛」不成立 ⇒ 判为 **「部分受钳制」**：**尾部（p90/max）由配置决定，中位数与多轮占比由机制决定**。

**【事实 · 两条口径提醒】**
1. **`max_turns` 钳的是 `turn_index`，不是消息条数**：mt=6 档消息 `max=16`、轮次 `max=6` ⇒ 按消息条数统计会得出错误的「超上限」。
2. **mock 不读语义**：本节**只谈深度、不谈自然度**（自然度需真 LLM + R3 指标）。

### 5.1b 两条会被读者误读的结构约束（先讲清）

**【事实 · 结构性下限】** `PUBLIC` 声道**恒为单条、不接话**，而 v0-anchor 中 PUBLIC 占 **48/187 ≈ 26%**。因此改造后 `single_msg_thread_ratio` **最多降到约 26% 附近，不可能接近 0**。正确写法是拆开看：
> 改造后单条线程占比 **X%**，其中 PUBLIC 单条声道构成约 **26%** 的**结构性下限**；DM/GROUP 侧的单发占比由 **91.3%** 降至 **Y%**。
**判断**：若不写这条下限，读者会把"还有约四分之一是单发"读成"改造没成功"——那是把声道设计误当成对话质量。

**【事实 · 有界设计】** 往复是**有界**的，不是"越长越好"：硬上限 `max_turns=6`、`max_turns_per_round=2`、`reply_window_rounds=2`、`history_turns=3`。因此指标按「**是否 >0**」「**是否 ≥4**」这类阈值判读，**不按"链越长越自然"**。最长链预期不会爆炸；若某臂最长链异常长，应先查开关是否被改，而不是当成好消息。

**【事实 · 轮数口径（写死，防放大 3 倍）】** **轮数 = 同一 `thread_id` 内 `turn_index` 去重后的个数**，不是消息条数、不是 `reply_to` 链长。按此口径复算 A0（本人直扫 `run.jsonl` (643f13a5)）：**206 线程，`turns` max = 6、p50 = 2、p90 = 6**；最长的 5 条线程都是 **6 轮**。

**【事实 · 为什么会出现"18"】** 消息条数 max 是 **18**，来自群聊线程 `TH-P009-Gplace-hall-67`：**18 条消息 / 只有 6 轮**——因为**同一轮内多名参与者并发发言**（群聊合法形态）。把"18 条"写成"18 轮"会把多轮深度**放大 3 倍**，属口径错误；本报告一律写作「**最长 6 轮（18 条消息）**」。

**【判断 · 6 轮不是「自然停止点」，是「上界被用满」】** 引用 6 轮时**必须一并写出上限值 `max_turns = 6`**：A0 的最长线程 **6 轮 == 上限**，说明**尾部被配置钳制**（上界被用满），不是对话自然收束。
> ⚠️ **旧表述作废**：本节此前写「属被截断」，现按 `max_turns` 三档 mock 对照（§5.1c）更正为「**上界被用满（尾部钳制）**」——差别在于：不是『对话被强行切掉』，而是『**只有尾巴能长到上限、中位数根本够不到**』。

因此：
- **不许用「最长 6 轮」论证「对话普遍自然」**；
- 甚至不能说「上界被用到了所以对话有深度」——**顶到配置上限只说明上限生效**，不说明内容需要那么多轮；
- 常态看 `p50 = 2`、`p90 = 6`；若要论证「多轮是自然发生的」，需要**把上限调高后的对照**，本轮没有；
- 推论：`max_turns` 提高或降低都会直接改变最长轮数——**这是配置效应，不是模型能力**，报告不得混为一谈。

## 6. 限制

1. **不做显著性检验**（§5.2）——结构层只给描述与事实对照，这不是遗漏，是方法上的正确做法。
2. **legacy 口径的 v0 数不能与新结构同口径比较**：表里已标 `thread_schema = legacy` 与 `n_threads = 212`，读者不应把 91.51% 理解为"新口径下改造前也是 91.51%"。
3. **单 seed、单批次**：线程长度分布的具体形状只在本配置下成立。
4. **字段契约以 D2 交付为准**：本报告在 D2 定稿后回填，若契约有变（字段名/上限/开关），§2/§3 同步修改并在提交信息里注明。
5. **"多轮"≠"自然"**：多轮只是必要结构条件。线程变长但内容空洞（互相复读、机械应答）在结构指标上"变好"，在质量层会暴露（见 R3），两者必须一起读。
6. **「多轮深度」这个变量本轮被配置钳住了**：最长轮数 `max` 恰等于 `max_turns = 6`（属被截断），所以本轮**观测到的"深度"上限是配置给的，不是模型给的**；`p50 = 2` 也说明多数线程根本没走到上限。因此本报告不对「模型能有多深」下任何结论。
   **可执行的后续（下一轮，零 LLM 成本，含预登记数值判据）**：做 **`max_turns` = 2 / 4 / 6 三档的 mock 对照**（同 seed、同 n、同 rounds，**唯一变量 = `max_turns`**），按下表**写死的判据**判读，避免事后争解释：

   | 判读 | 数值判据（三档 = 2 / 4 / 6） |
   |---|---|
   | **继续增长 ⇒ 配置是瓶颈** | `p50` 随上限提高**单调上升**，**且** `p90` **至少提高一档**（例：2→4 时 `p90` 由 2 升到 ≥3） |
   | **早收敛 ⇒ 模型/提示词是瓶颈** | 三档 `p50` **相同（差 ≤1 轮）且** `p90` **不随上限变化** |
   | **部分受钳制** | 以上两者之外：须写明**从哪一档开始不涨**（例：2→4 涨、4→6 不涨 ⇒ 瓶颈在 4 轮附近） |

   三条边界同样写死：① mock **不读语义**，只谈「深度是否被配置钳住」，**不谈「多轮内容是否自然」**（后者需真 LLM + R3 措辞指标）；② 三档必须同 seed / n / rounds，否则不可比；③ 零真钱成本，不占用 A1 的真 LLM 预算。
