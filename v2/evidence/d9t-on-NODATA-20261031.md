## 4. 对后续所有真 LLM 臂的系统性含义（**比 D9t 本身重要**）

> **观测事实**：进程 `poll` 等 socket、连接 `ESTAB`、本地源端口变化（超时重连），`run.log` 0 字节。
> **但"无限挂"这一条尚未验证**——代码里 `providers.py:25 DEFAULT_TIMEOUT = 60`、`max_retries = 2`（有界）：
> `grep -n "DEFAULT_TIMEOUT\|max_retries" code/freeze/providers.py` ⇒ `25: DEFAULT_TIMEOUT = 60`、`237: max_retries: int = 2`。
> ⇒ **重试是有界的**，理论上 3 次尝试（≈3×(60s+backoff)）后会抛错落 `SYSTEM_ERROR`；
> 而我们两次都在 ~2–4 分钟内 kill，**可能没等到它自己报错**。
> **⇒ 结论改成：卡点在"超时重连循环"这一点确定；"它会不会自己结束"未验证——而且已算出它"来不及结束"。**

**时间对账（决定性）**：
```
单次 complete() 最坏 = 60s × (max_retries+1) + (0.5+1.0) = 181.5 秒   （providers.py L25/L237/L238）
第 5 批：17:43:11 启动 → 17:46:03 判 STALLED = 172 秒  ⇒ 早了 9.5 秒被杀
```
⇒ **它当时很可能正走在"第 1 次 60 s 超时 → 退避 → 第 2 次"的路上，真正的 `RuntimeError` 从未有机会写出。**
⇒ **`run.log` 0 字节不是"卡死无输出"，而是"异常还没抛，所以当然为空"** —— 0 字节其实是**"仍在正常重试路径上"**的证据。

**判死判据（改写，替代"N 分钟行数不动"）**：
1. 先算窗口：`60 × (max_retries+1) + backoff = 181.5 s`；**低于此秒数的零增长属正常**；
2. **等到 `run.log` 出现内容**才算终结（真失败必写 traceback）；
3. 想快就把 `DEFAULT_TIMEOUT 60→20`、`max_retries 2→1`（窗口压到 ~41 s，代价是更易被瞬时抖动误判）。

⇒ **修法（下一次跑批前必须先做）**：
1. 给 HTTP 客户端设**读超时 + 有限重试**（例如 `read=120s`、`retries=3`），超时即抛错并落 `SYSTEM_ERROR`；
2. 批任务外层加**墙钟上限**（如 `timeout 3600`），并把退出码写入 `launch_cmd.txt`；
3. 起跑后 **60 s 无新增事件即抓 `wchan` + `ls -l /proc/PID/fd`**，把"等"与"死"分开。
