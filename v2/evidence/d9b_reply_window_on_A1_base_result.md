## 4. 机制命中量：`reply_lag` 分布（本件的核心证据）

`reply_lag` = 回复所在 `round` − 父消息 `round`（父消息经 `msg_uid` 索引，**0 未命中**）。

| lag | ctrl（rw=2） | treat（rw=4） |
|---|---|---|
| 1 | **656**（98.94%） | **656** |
| 2 | **7**（1.06%） | **7** |
| **≥3** | **0** | **0** |
| 合计 | 663 | 663 |

- **每线程最大 lag**：`{1: 121 线程, 2: 6 线程}`，两臂相同。
- **`lag ≤ window` 覆盖率**：ctrl 663/663 = **100.00%**（window=2 已覆盖全部回复）。
- **treat 臂 `lag≥3` 回复数 = 0** ⇒ window 从 2 放宽到 4，**多出的两轮容量从未被使用**。

**尾截断处理**：run 最大 `round` = 83，可观测 `lag≤4` 的样本 = 父消息 `round ≤ 79`，共 **638 / 663 = 96.23%**；被排除的 25 条全在尾部（父消息 round 80–82），其 lag 只有 1–2，**不改变"lag≥3 = 0"**。

## 6. 机制诊断（比判定更重要）：瓶颈是**挑选顺序**，不是**容量**

lag 分布几乎全压在 1（98.94%），2 只有 7 条（1.06%），3 及以上为 0。看代码可以解释：

- `agent.py:979` `_pick_reply_target`：**按 `seq` 倒序遍历可见事件（最近优先），取第一条满足全部条件的**。
- ⇒ 只要还存在一条 lag=1 的未回入站，agent **永远不会**去接 lag=3 的那一条；窗口放宽对"最近优先"的挑选顺序毫无影响。
- ⇒ 窗口长度不是"接话多久才允许"，而是**"多久之后就再也不允许"**；在当前行为下所有接话都在下一 slot 内完成，这个上限**从未逼近过**。

**这给出下一个真正的嫌疑点**：`_pick_reply_target` 的「最近优先」序。若目标是"隔几轮才回"的生活感（真人会拖着回话、会隔一顿饭才想起回应），该改的是**挑选顺序**（如"欠得最久的优先"或按关系强度加权），**不是窗口**。但那是新预登记，本件不擅自扩展。

## 7. 局限（随结论一起引用）

1. **mock，无语言生成** ⇒ 本件只说结构量；**不得**据此对「对话是否更有生活气息」下任何结论。
2. **单 seed（42）、单臂各一次**；mock 确定性下不需重复，但**跨 seed 是否仍为 0 差异未验**（不主张）。
3. lag 由 `msg_uid` 回指父消息计算，**0 未命中**；但 `reply_to` 缺失的 MSG（929−663 = 266 条）按"发起"处理，与 `_initiate` 语义一致，未额外核。
4. 与 D9 旧结论并引时必须写：**「旧 = 旧结构（回复被 slot 配额卡死）下惰性；新 = A1 基座下仍是零行为差异」**，不得写"推翻 D9"——前提变了，不是 D9 算错。
5. **不得与 A2 合并**成"回复类参数都无效"的总账：A2 是"机制几乎未触发"，本件是"机制触达但容量未用满"，**两者证据形态不同**。
