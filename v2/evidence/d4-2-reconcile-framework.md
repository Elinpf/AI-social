## 1. 第一道闸（**最重要，不过则对账无意义**）：事件是否真的在落

`T-RIFT-EVENTS` 回来后，**第一件事不是对账，是确认新事件与既有台账/快照自洽**：

| # | 检查 | 不过的后果 |
|---|---|---|
| ① | `RIFT_OPEN` 事件数 == 台账登记数 | 事件漏写或多写 ⇒ 总数不可信 |
| ② | `RIFT_CLOSE` 事件数 == 台账注销数 | 同上 |
| ③ | **`dialogue_rift` 快照对得上**：每条快照的 `open` 值 == 该 `seq` 时刻「已 OPEN 且未 CLOSE」的 rift 数 | 快照与事件流是两套账 ⇒ **拿两套不知真假的数比大小** |

⇒ **③ 是新增的关键一条**：它把"新事件"与"今天已有的快照"钉在一起。**只有 ③ 过了，`RIFT_OPEN` 才算可信台账。**

## 2. 对账口径表

### 2.1 新口径（`RIFT_OPEN` / `RIFT_CLOSE`）

| 量 | 定义 | 性质 |
|---|---|---|
| **`rift_total`** | `RIFT_OPEN` 事件计数（= 登记的 rift 数） | **真实总数**（含从未被修复者） |
| **`rift_repaired`** | `RIFT_CLOSE` 中**原因为修复**的 `rift_id` 去重数 | 修复数 |
| **`rate`** | `rift_repaired / rift_total` | D4-2 和解率 |
| **交叉核对** | `rift_repaired` 应 == `dialogue_repair.rift_ids` 去重数（同一事物） | 不等 ⇒ 两套账不一致，停 |

### 2.2 与旧值的差值分解（**这是对账真正的产出**）

```
新 rift 总数  =  已修复（rift_repaired）  +  未修复（= "沉默的 rift"）
                 └─ 这一项 ≈ 旧值（今天的 7 / 16 / 0）
delta          =  新 rift_repaired  −  旧 rift_repaired
delta_explained =  rift_total − rift_repaired
```

**判据**：**`新 ≥ 旧` 且 `delta == delta_explained`**。

⚠ **反向提醒（必须同屏）**：**两值"正好相等"反而说明新口径没起作用** —— 那时 `delta_explained` 会是 0，意味着根本没有"沉默的 rift"被数出来，**值得怀疑 `RIFT_OPEN` 是否真在落**。

### 2.3 今天的旧值（作对账基准，**不由本脚本计算**）

| 批 | 旧 `rift_repaired`（`rift_ids` 去重，精确） |
|---|---:|
| `emo-on-20261029` | **7** |
| `run_f4_on_n16r60_seed42` | **16** |
| `run_r6_treat_n16_seed42` | **0** |

⇒ 由 `--old-rift-repaired` 传入，**不写死在脚本里**（避免"脚本里的数是猜的"）。

## 附录：Leader 采纳一条"第零步"（`repro-verifier` 2026-11-01 23:1x 提出）

**问题不是"字段名对不对"，而是"名字对、取值域错"**：
> 脚本预期 `RIFT_CLOSE.reason ∈ {"repair","fix"}`；实现方实际给 `{"repaired_by_word","expired"}`
> ⇒ **名字对上了、脚本也跑通了，但"修复"这个判定会静默漏掉一半。**

⇒ **对账前先做"第零步"**：
1. 要一份实现方**字段清单**：`事件类型 → 字段名 → 取值域/样例值`；
2. 脚本与之**逐项比对**，不一致 ⇒ **改脚本**；
3. **对 `reason` 这类取值域字段，必须看样例值**，不得只看字段名。

**并写死**：取值域不同 ⇒ **改脚本常量并记一笔**，**禁止在数据侧做映射**（那等于改数据适配脚本）。

> **同族第 11 例的近亲**：第 11 例是"脚本跑通但读的是**猜的**字段名"；本条是"**名字对、含义错**"。
> 两者共同点：**脚本能跑通，且不报错** —— 危险恰在此。
