## 0. 一句话

上两轮我们把卡点归因为「服务端不回 + 客户端重试」。**代码事实查到了，比推断更精确**：
**客户端有 60s 读超时 + 2 次重试 = 181.5 秒窗口；而第 5 批是在 172 秒被判 STALLED 的 —— 早 9.5 秒，真正的异常从未有机会抛出。**

## 1. 代码事实（`code/freeze/providers.py`，可复算）

```
L25    DEFAULT_TIMEOUT = 60                        ← 60 秒 socket 超时（不是"没有超时"）
L237   max_retries: int = 2                        ← 共 3 次尝试
L238   retry_backoff: float = 0.5
L266   urllib.request.urlopen(req, timeout=self.timeout)
L273-276  HTTPError 429/5xx → 退避重试
L279-283  (URLError, TimeoutError, OSError) → 退避重试 → 仍失败则
          raise RuntimeError("OpenAI 兼容端点不可达/超时")
```
**窗口计算**：`60 × (2+1) + (0.5×1 + 0.5×2) = 180 + 1.5 = 181.5 秒`
⇒ 单次 `complete()` **最坏 181.5 秒后必然抛异常**，异常会被 `2>&1` 写进 `run.log`。

## 2. 时间对账（第 5 批 `run_id=174311`）

```
启动     17:43:11   (launch_cmd.txt started_at)
被杀     17:46:03   (目录被改成 .STALLED.174603)
实际存活 172 秒
超时窗口 181.5 秒                 ⇒ **早 9.5 秒**
progress.tsv: 17:44:15 34 13149 alive / 17:45:15 34 13149 alive（两次采样均 alive）
```
⇒ 它当时极可能正处于「第 1 次 60s 超时 → 退避 → 第 2 次 60s 超时 → 退避 → 第 3 次」的路上，**第 3 次没走完就被 kill**。

## 3. 这条改变了一个解释（重要）

| 原解释 | 修正后 |
|---|---|
| `run.log` 0 字节 = "卡死、无任何输出" | **`run.log` 0 字节 = "异常尚未抛出"** ⇒ 这是「**还在正常重试路径上**」的证据，**不是卡死的证据** |

⇒ 所以"四次（五次）启动全卡死"这个说法**过强**：我们只知道它们**在 172–180 秒内没有产出**，**从未观测到它们"超过 181.5 秒仍不报错"**。
要证明"真卡死"，必须观测到「**超过 181.5 秒 + `run.log` 仍为空**」。

## 4. 修法建议（取代"加读超时"，因为超时本来就有）

1. **判卡死前先算窗口**：`60×(max_retries+1)+backoff = 181.5s`；低于此的零增长是**正常重试中**，不是卡死；
2. **判据改成"等 `run.log` 出现内容"**（真失败必写 traceback），而不是"N 分钟行数不动"；
3. 若嫌 181 秒太长：`DEFAULT_TIMEOUT 60→20`、`max_retries 2→1` ⇒ 窗口压到 ~41 秒（代价：更易把瞬时抖动判成失败）；
4. **必须保留 `-u` + `2>&1 | tee`**（否则连 traceback 都看不见）。
