## 1. Q2：`9db4e9cd` 的真相（不是"值不存在"）

```
$ git cat-file -e 9db4e9cd^{commit}  → rc=128   （不是 commit）
$ git cat-file -e 9db4e9cd           → rc=0     （是 git 对象）
$ git cat-file -t 9db4e9cd           → blob
# 它对应哪个路径：commit 1774c20 的
v2/refs/D9t-blocker-B1-wrong-code-base.md
# 当前版对比：
B-1 件当前 blob = 09227b6d…；当前 sha256sum = 064dd6c1…
```
⇒ **`9db4e9cd` = B-1 阻断件在 `1774c20` 那一版的 git blob sha**，是真实存在的历史对象。
⇒ 旧版脚本只查 `^{commit}` ⇒ 报 MISSING 属**查法不对**，不是值错。**这条你判断正确。**

## 2. Q1：双查的副作用 —— 从"假 MISSING"变成"假 OK"

新版双查会把 `9db4e9cd` 归为 `object` 类 ⇒ **打印 OK，不报警**。
但它的实际身份是"**历史版文件的 blob**"（当前 B-1 件已变成 `09227b6d…`）。

⇒ 后果：**读者在清单里看到 `9db4e9cd` 被判可核，会以为它指向当前 B-1 件，实际指向 `1774c20` 那版。**
这与今晚 `d5c386e`/`d7dab02`「A2 缺失态」是同一类风险：**对象存在 ≠ 指向的是当前版本**。

这正是你自己立的 §9.2 纪律「引用历史件先 `cat-file -e` 再读」不够用的地方——
`cat-file -e` 只能证明"对象在"，**证明不了"它是当前版"**。而脚本现在把"对象在"当成终点了。

**建议加第三层（可机械判）**：
```bash
# blob 是"当前版"还是"历史版"？
if git ls-tree -r "$REV" | grep -q "$(git rev-parse "$tok")"; then
  echo "object(当前版)"
else
  echo "object(历史版) —— 须显式标注'历史版/时点记录'"
fi
```

## 3. Q3：白名单可绕过（**实测复现，这是最要紧的一条**）

白名单判据是「**同行**出现 `不存在|已废弃|作废|未入库|未落地|MISSING|文本切片|字符串级|内容 sha|修订史|历史版` ⇒ 该 sha 放过」，且 `continue` 作用于**整行所有 sha**。

**我造的测试件（4 行）与实跑结果**：
```
L2  正确引用：`78ec29a658f80242` 见 v2/refs/D9t-launch-checklist.md
L3  错误 sha 但同行有"修订史"：`deadbeef12345678`（修订史表见下）
L4  两个 sha 一行，一个好的一个坏的：`78ec29a658f80242` 与 `badbadbad999`（历史版说明）
L5  真错误无任何词：`cafebabe1234`
```
```
  **BAD(content 不符)** L2  78ec29a658f80242   ← 清单已再改，实际 2b1cd757…（正常，见 §4）
  已声明缺失    L3  deadbeef12345678            ← ✗ 死 sha 被放过
  已声明缺失    L4  78ec29a658f80242            ← 整行免检
  已声明缺失    L4  badbadbad999                ← ✗✗ **坏 sha 逃过检查**
  **BAD** L5  cafebabe1234                      ← ✓ 无标注的才被抓
```
⇒ **两个漏洞，实测确认**：
1. **一行有标注词 ⇒ 该行所有 sha 全部免检**；L4 里 `badbadbad999` 与一个以 `bad` 开头的伪 sha 一起"合规"通过了。
2. **白名单词过于日常**：`修订史`、`历史版`、`内容 sha` 这些词在正常文档里到处都是（本清单自己就有"修订史（引用旧 sha 时须能对上…）"），**一句话就能让整行免检**。

**这不是说你的件有问题**（你的清单自跑 20 个 sha、漏 0、ALL_EXPLAINED，我复跑一致），而是说**脚本作为"守门人"是可被绕过的**——而它最容易漏的正是"一行多 sha"的场景，**而 `L176` 就是一行两个 sha（`cef1c58` commit + `5ca75d76` 内容 sha）**，这不是假设。

**建议修法（两条，都很轻）**：
1. **白名单只作用于"紧邻该 sha"的窗口**（如该 sha 前后 20 字符内），而非整行：
   ```bash
   ctx=$(printf '%s' "$line_text" | grep -oE ".{0,20}${tok}.{0,20}")
   printf '%s' "$ctx" | grep -qE '不存在|已废弃|未入库|MISSING|历史版' || { 报漏; }
   ```
2. **`--strict` 把"已声明缺失"也算待审**（至少打印清单让作者逐条确认），否则 strict 只约束"待配"，不约束白名单。
