# 补正：六维评估「③误会与和解 = 无（0/686）」是**机制未启用**，不是"模型不会"

> 立件：Leader（team-leader）｜2026-10-29
> 本件**补正** `v2/evidence/d9e-lifeliness-sample-review.md`（`cb824884…` / 212 行）中「③误会与和解 → **无**，误会/致歉类词 0/686 = 0.00%」这一条的**解读**。
> 数值不变（0/686 是真的），**但"无"这个判词会被读成"AI 小镇不会误会与和解"——那是错的。**

## 1. 事实：该机制**默认关闭**，三个臂跑批时都是关的

`code/config/dialogue_repair.json`：
```json
{ "enabled": false,          ← 总开关，默认关
  "gripe_context": true,
  "reply_priority": true,
  "window_msgs": 8, "max_open": 3, "max_age_rounds": 84,
  "context_max_age_rounds": 24 }
```

三臂实测（我逐条 grep）：

| 臂 | `dialogue_rift` 字段命中 | 跑批 env `HITT_DIALOGUE_REPAIR` |
|---|---|---|
| `run_d9_a1_n16r84_seed42` | **0** | **未设** |
| `run_d1_f6off_seed42_n16r84` | **0** | **未设** |
| `run_meal_on_n16r60_seed42` | **0** | **未设** |

`dialogue_rift` 只在 `enabled` 且确有未了结 rift 时才会写进 payload（模块 docstring 原话：「关闭时日志中**一条都没有**」）⇒ **0 命中 = 模块从未运行**，不是"I/O 缺陷"、也不是"识别到了但没和解"。

另：`dialogue_repair.json` **不进** `engine/version.py::FINGERPRINT_FILES`（原注释明写"刻意选择"）⇒ `meta.json` 的 `config_components` 里查不到它（实测 grep 为空）。

## 2. 正确的判词与解读

| 错误说法 | 正确说法 |
|---|---|
| ③误会与和解 **无**（AI 小镇不会误会与和解） | ③误会与和解 **未启用**（机制存在、代码完整、开关关着，故无任何观测） |

按纪律，这属于 **「机制未启用（开关未开）」**，与 **「无效」**、**「机制未生效（指令未被执行）」** 是三个不同的判词，**不得混用**。本件只主张前者。

## 2.1 严格限定：**"跑批当时的开关值"属 CANNOT-VERIFY**（2026-10-29 由 `prompt-linguist` 指出，采纳）

我原写「三臂跑批时都是关的」，**这句过头了**。严格说，我能证的只有三条：

| 证据 | 强度 | 能证什么 | 不能证什么 |
|---|---|---|---|
| `config/dialogue_repair.json` 当前为 `enabled: false` | 代码/配置层 | **默认值**是关的 | 跑批当时是否被 env 或 override 打开 |
| 三臂 `dialogue_rift` 命中 **0** | 日志层 | 日志里**零痕迹** | 是"关着"还是"开着但没有 rift" |
| 跑批 env **未设** `HITT_DIALOGUE_REPAIR` | 环境快照 | 该次跑批的 env 里没有它 | env 快照本身是否完整（`env_dump_pre.txt` 的已知局限） |
| `dialogue_repair.json` **不进** `FINGERPRINT_FILES` | 设计事实 | `config_digest` **不可能**记录它 | —（这条恰恰说明：**无法用 digest 反证当时的开关值**） |

⇒ **规范措辞**（此后一律照写）：
> 「机制**在代码层默认关闭**、**当前配置为 `false`**、且**两臂日志零痕迹** ⇒ 该维度未产生内容的**主因是机制未启用**；但**跑批当时的具体开关值无法由日志与 `config_digest` 确证（CANNOT-VERIFY）**。」

**为什么这条限定必须写**：第四条证据是"该 config 不进指纹"，它既是"打开不影响旧日志复现"的设计优点，也同时意味着**事后无法从任何日志反查当时的开关值**。把"日志零痕迹"当成"确证当时关着"，就是又一次把"结构性可见性不足"当成"观测证据"。

## 3. 这条补正为什么重要

1. **它把 ③ 从"能力缺口"改成"待测项"**：六维里唯一被判"无"的一维，其实**从未被检验过**；
2. 若不补正，读者/后续报告会写"AI 小镇在误会与和解上是空白"——这是**用"没开"冒充"不会"**，与我今天修的四个同族错误（把结构性必真/结构性空值当证据）属同一类；
3. 它同时给出**一个成本极低的下一步**：整个模块已实现（`code/life/dialogue_repair.py`，含 `gripe_context` / `reply_priority` / `TOOLBOX` / `dialogue_rift` 结构化信号），只需 `HITT_DIALOGUE_REPAIR=1` 即可第一次检验。

## 4. 若要检验，必须先写死的三件事（预登记要点）

1. **判据不能是"误会类词命中 > 0"**：那是 ③ 的**结果**指标，会被"词表漏项"和"措辞差异"主导。应先报**机制命中量**：`dialogue_rift.prompted = true` 的消息条数 / `route="reply_priority"` 的条数 / `open > 0` 的条数。按 `v2/refs/hit-metric-h0-baseline-rule.md`，每个量都要报 **H0（关 DR）下的取值**——已知 H0 下全部为 **0**，故它们有区分力。
2. **必须披露 `reply_priority` 是干预**：它改的是"回复时优先挑有旧账的线程"，属**相遇/回复优先级干预**，**不是**"居民自发产生冲突"。报告须写成「干预了回复优先级」，与"自然发生的误会"严格区分（模块 docstring 已自陈这一点）。
3. **代价闸**：开 DR 后 `MSG` 总量、`≥3 轮` 绝对条数、`lag` 分布是否变化；若 `MSG` 掉超 10% 则判"用少说话换和解"，不报为改进。

## 5. 局限

1. 本件是**配置/日志层核查**，未跑任何实验；"开 DR 后能否产生误会与和解"**仍是未验证问题**。
2. 词表镜像（`NEG_WORDS`/`REPAIR_WORDS`）是上游 `tools/d5/*_lexicon.txt` 的**子集**（测试守住"不漂移"）⇒ 即使开了 DR，**用词表层衡量"和解"仍可能漏检**；这与判据 1 的关切一致。
3. 本件不改六维评估的任何数值，只改 ③ 的**判词与解读**；评估件按纪律不覆盖，原 `cb824884…` 留档。
