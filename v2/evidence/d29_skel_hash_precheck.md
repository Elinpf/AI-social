# D2.9 离线预检：**`skel_idx = sha256(...) % 5` 在 n=149 上极差 8.1pp，达不到预登记的"20±3pp"**

> 日期：2026-10-25 01:28。**纯离线预检**（用 D2.8 的 B 臂 (thread_id, turn) 集合，不跑批）。
> 目的：在 D2.9 实现落地前，先验证"哈希分骨架"能不能真的均匀。

## 1. 实测（两个 seed 完全相同，因哈希确定性）

D2.8 的旁白集合（= `para_on=True` 的 (tid,turn)，**n = 149**）：

| `skel_idx` | 条数 | 占比 |
|---|---|---|
| 0 | 36 | **24.2%** |
| 1 | 24 | **16.1%** |
| 2 | 32 | 21.5% |
| 3 | 27 | 18.1% |
| 4 | 30 | 20.1% |

**极差 = 24.2 − 16.1 = 8.1pp**。

## 2. 两个问题（一个是标准的，一个是设计的）

### 2.1 预登记的 mock 标准 `20±3pp` 对 n=149 **不切实际**

5 分类、n=149、p=0.2 ⇒ 单类计数标准差 = √(149×0.2×0.8) ≈ **4.9 条 = 3.3pp**。
即 **1σ 就是 3.3pp**，`±3pp` 容差等于要求"5 个类别全部落在 1σ 内"，概率极低。
⇒ 该标准应用 **±6pp（约 2σ）**；这是**标准定错，不是实现错**。

### 2.2 但 `%5` 哈希**确实**不均匀：极差 8.1pp ≈ 2.5σ

即便放宽到 ±6pp，`skel0=24.2%` 仍接近上限。更根本的问题是：
**哈希只能"近似"均匀，而本臂的目标恰恰是"均匀覆盖 5 种骨架"** —— 用哈希追均匀是绕路。

## 3. 建议改设计（**在实现落地前**，改动极小）

把"哈希选骨架"换成"**按旁白序号轮转**"：

```
skel_idx = (该 agent 至今写过的旁白条数) % 5      # 确定性：同 seed 同顺序 ⇒ 同结果
```

- **精确均匀**：149 条旁白 ⇒ 5 类各 29–30 条（20.0% ± 0.7pp），**不再需要放宽容差**；
- 仍**确定性**（不引入随机数，符合项目纪律）；
- 与 `para_on` 天然独立（一个按 (tid,turn) 哈希、一个按计数轮转）⇒ 交叉表必然均匀；
- **代价**：需要 agent 持一个旁白计数器（`self._para_counter`），**新增一个状态字段** ——
  属于"结构级"小改动，但**不影响任何已有行为**（只在 `para_on=True` 时读它）。

**若坚持用哈希**：必须把 mock 容差改为 **±6pp**，并在预登记里写明"哈希均匀性受 n=149 限制"，
同时**判据里的 `骨架 TOP1 ≤30%` 仍然可判**（24.2% < 30%），所以**判定本身不受影响**。

## 4. 结论

- **判据不用改**：`把` 开头 ≤25%、骨架 ≤20%、TOP1 ≤30% —— 按 24.2/16.1/21.5/18.1/20.1 的分布，
  只有 `骨架 ≤20%` 会被 `skel0`（24.2%）顶到**边界**（`把N往/在P一V` 恰是 skel0）；
- 但**实现若换用轮转，分布立刻精确到 20±0.7pp**，更符合"我要的是均匀"这个设计意图；
- **mock 容差 ±3pp 是标准定错**（1σ=3.3pp），建议改 ±6pp；若改用轮转，可继续用 ±3pp（因为会真的均匀）。
