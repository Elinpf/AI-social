## 方法（为什么不 tracemalloc）
`tracemalloc` 为每处分配记录调用栈，在 N=20×84 上数值**失真且放大内存**（实测 round0 traced=1102MB 而 RSS 仅 42MB）。故改用 **`gc.collect()` + `sys.getsizeof` 深遍历**（纯 Python，无调用栈记录），**仅 4 个快照**（r20/41/62/83），并对**所有类别用同一个 `seen` 做全局去重**（共享对象只计一次，避免 T268 共享正文被重复计数）。

### ★ `life.forward_state` 行：**一处结构，两个病**
> 该行（`_observed_seqs_` 等）**同时是 T276（flush 前缀续跑逐字节一致）的正确性障碍**：
> 它**只前向累积、不可由 `perceive()` 重建** ⇒ 续跑新进程会**重观测**。
> **T272 是"内存为什么涨"，T276 是"续跑为什么分叉"——同一个结构。**
> 计数实测：`observed_seqs_total` r20=14683 → r83=**58125**（**≈ +688/回合**，即 ~34/agent/回合）。
> 注：**它按 MB 很小（浅尺寸 <1MB）**——它不是内存主因，**但它是正确性主因**。两病同一结构、不同量级，勿混。

## 未定位（如实标注，不凑表）
`~4.55 MB/回合`（占 RSS 增长 ~54%）**未归到具名结构**。**未定位≠无增长**。最可能的去处（**未验证**）：
- Python 分配器/GC 开销、"已归因"对象的**深遍历未覆盖**的容器（如 `engine` 的 production/inventory 侧结构、`freeze`/`obs`/`orchestration` 持有的对象）；
- `dict`/`str` 的**共享与驻留**（intern）导致 `getsizeof` 低估或分类交叉；
- 平台侧其它进程叠加（分析时段平台 anon 已 6.9G）。

## 结论（R8 剩余部分）
1. **增长主项 = `ledger.records`（账本事件全量常驻内存，3.07 MB/回合、占已归因 79%）** —— **不是记忆正文**（T268 已解）。
   → **R8 的下一个真解应打在"账本常驻"上**：分段/流式落盘 + 只保留可重建的索引（与 T262 flush 同族思路），**属改结构不改语义，需 08 先定口径**。
2. **次项 = `engine.state`（0.535 MB/回合）**，其中包含每 agent 的 `memories` 索引与 `observed_event_seqs`。
3. **记忆节点 0.283 MB/回合**（T268 后已很小）；**life 前向态 MB 极小但为 T276 正确性障碍**。
4. **外推**：按已归因 3.89 MB/回合（且账本项本身超线性：r20→41 增量与 r62→83 增量比 ~1.9×），N=50 仍会到 **GB 级**；**未定位 54% 需进一步定位后**才能给出可靠的 N=50 上界。
