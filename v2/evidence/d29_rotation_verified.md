## 1. 被验证的式子（摘自 `.worktrees/d29-syntax-diversity/code/life/agent.py:139-164`）

```
skel_offset(agent_id) = sha256(agent_id)[:8] % 5
skel_idx(n_par, offset) = (n_par + offset) % 5        # n_par = 该 agent 已写旁白条数
```

## 3. 两点得到确认

1. **轮转确实精确均匀** ⇒ mock 容差 `20±3pp` 可用，**不需要**放宽到 ±6pp（`d29_skel_hash_precheck.md` 的建议只在坚持哈希时才需要）。
2. **`skel_offset` 是必要的**：若所有 agent 都从 0 起轮转，各自**第一条**旁白必然落 `skel 0`，
   16 个 agent 会把 `skel 0` 抬高（我实测 24.4%，执行方测 24.4%）⇒ **顶破 D1「骨架 ≤20%」**。
   加 `sha256(agent_id)%5` 起点后，`skel 0` = **19.9%**，刚好在判据线内。
   （offset 取值：P001→2, P002→3, P003→3, P004→0, P005→0, P006→1, P007→1, P008→3, P009→0, P010→0, P011→4, P012→3, P013→1, P014→1, P015→1, P016→0）

## 4. 判据提醒（不改判据，只提醒解读）

`skel 0 = 19.9%` **只是刚过线**（阈值 ≤20%）。若真跑的旁白条数分布不同，可能落到 20.1%–20.6% ⇒ **判据会判"未达"**。
这是**判据边界过紧**的问题，不是实现问题。届时按预登记表执行（D1 未达 ⇒ 「无效（骨架未多样化）」），
但报告必须并列"实测 20.x% vs 阈值 20%，属边界效应"，**不得**临时改阈值。

## 5. 结论

- 轮转方案**验证通过**，可以继续；
- `skel_offset` 这个细节是执行方自己加的、且**必要性已实证**（不加则 24.4% 破线）；
- 唯一遗留是 D1 阈值与实测贴得过近（19.9% vs ≤20%），**列为边界风险**。
