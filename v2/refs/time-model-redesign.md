## 0. 结论速览（先结论，后证据；**含"用户对了一半"的诚实判定**）

1. **「所有 Agent 同一时间一起涌入」——一半成立，必须分开谈**（§1）：
   - ✅ **成立（且是 R1 的真主因）**：每回合**全体 Agent 都被评估**（`kernel.py:150`），且**每次评估都从账本"从头全量重扫"**（`life/visibility.py:42` / `engine/perceive.py:41`）。**T254 实测这是 CPU 头号热点**：`visible_events`+`location_of` 占 `11.2M` 次 `_visible`、全局 `158M` 次 `dict.get`（N=20×24）。
   - ❌ **不成立**：**并非"全体同时调 LLM"**。LLM 早已按触发门控（importance 仅对新事件、plan 每周一次、reflect 到期 —— `agent.py:163/104/373`）。
2. **R1 的真主因是"每 tick × 每 agent × 全量重扫"的 CPU（非 IO）**：T254 §6.1 **IO≈0（<1%）**（磁盘 90.0s vs /dev/shm 89.2s）；超线性 ≈ `O(N²·rounds²)`（R=24→40s、R=84→390s，rounds×3.5→时间×9.75）。
3. **最省的第一步不必改 tick 语义**：**"增量/每回合只索引一次可见性"**（T254 §6.5 **c2 已批·首选**）即可吃掉重扫的 **~N 倍因子**，**且输出逐字节不变（无失真）**。→ **先做 c2/c1，再谈改 tick。**
4. **"事件驱动 + 按需唤醒"仍有价值，但别高估**：在 N 大时，**每回合几乎总有事件可观察 → 唤醒几乎恒真**（importance 超线性即此现象）→ **对 CPU/LLM 的边际节省有限**；它的真收益是 **语义拟人（满足用户直觉）+ 并发错峰 + 为"个体节奏/异步分时对话"（用户目标#1）铺路**。
5. **推荐（摆选项，非预设）**：**乙+ 双时钟** —— **保留离散回合作"世界结算节拍"**（84 回合/周、每回合结算不变），**新增"个体决策节拍"（确定性唤醒集 W1–W6 + 到期调度）**，**感知改增量**（c1/c2）。**不建议连续时间（丁）**：与结算/审计/统计契约冲突、内核级重写，收益（临场感）可在表现层单独补。

## 1. 现状核实：tick 到底是什么、一个回合里谁在动（**带证据**）

### 1.1 时间语义（现状）

| 层 | 换算 | 来源 |
|---|---|---|
| 回合 round（tick） | 引擎最小节拍，**每回合结算**（P3.5 LIFE + P4 ARBITRATE + P6 COMMIT） | `kernel.py:189 run_round` |
| 时段 slot | 3 回合 | `config/default.json time_config` |
| 日 | 4 时段 = 12 回合 | 同上 |
| 周 | 7 日 = **84 回合** | 同上 / `v1.1/00-architecture.md §3` |

派生纯函数：`code/engine/time.py:18 derive_time(round) → {week,day,slot,...}`（无墙钟）。

### 1.2 一个回合里，是否所有 agent 都决策/行动？

**是——全体被"评估"；但 LLM 调用已被触发门控。**

```
kernel.py:254  run(rounds):  for r in range(rounds): run_round(r)          # 串行全局时钟
kernel.py:147  phase_decide: for agent in sorted(self.agent_steppers):     # ← 每回合遍历【全体】
                                 agent.step()
kernel.py:139  phase_route:  return None                                   # ← "W1–W6 唤醒集合"【从未实现】
kernel.py:143  phase_perceive: return None                                 # ← "为被唤醒 Agent 建 view"【从未实现】
```

`agent.step()`（`life/agent.py:126-146`）每回合对每个 Agent 跑一串子步骤，但 **LLM 仅在这些门控成立时才被调用**：

| 子步骤 | 触发门控 | 证据 |
|---|---|---|
| importance | 仅 `seq ∉ self._observed_seqs` 且 `type ∈ _SALIENT_EVENTS` 的**新事件** | `agent.py:163-172` |
| plan | **每周一次** | `agent.py:104-105` |
| reflect | **累积重要性/周到期** | `agent.py:373-376` |
| judge/narrate/negotiate | `_maybe_*` + M4 许可 | `agent.py:212,84-101` |

> **判定**：「一起涌入」**在"评估"侧成立，在"LLM"侧不成立**。

### 1.3 现状代价 —— T254 实测（**这是 R1 的主因**）

`v2/evidence/n50-m4-probe.md`（探针 sha `d65abf1`，N=20×24 mock，`[DIRTY—参考值]`）：

| 事实 | 值 | 出处 |
|---|---|---|
| **IO 不是瓶颈** | 磁盘 90.0s vs /dev/shm 89.2s → **IO≈0.7s（<1%）** | §6.1 |
| **CPU 头号热点** | `visible_events`(`life/visibility.py:42`)+`location_of`(`:13`)：**11.2M 次 `_visible`、全局 158M 次 `dict.get`** | §6.2 |
| **回合内超线性** | R=24→~40s；**R=84→390s**（rounds×3.5 → 时间×9.75）⇒ ≈ `O(N²·rounds²)` | §6.2 |
| 超线性根因 | `MEMORY_WRITE` 66% 由 `RELATION_CHANGE`（**逐共处对 pairwise**）触发，观察扇出 ≈2.65 | §1 |
| M4 不是解药 | M4/M6 开：调用 −67%，**时间仅 −25%**，**且 `state_hash` 变（改行为）** | §2 |
| 内存第二根因 | RSS +5MB/回合（N=20，peak 493MB），**无平台** → N=50 外推 GB 级 → 宿主 OOM 方向 | §6.3 |

**"全员每回合行动"占多大比重？** —— **是当前 CPU 的支配项**：`visible_events`/`location_of` 是 #1 热点，而它正是 **`N × rounds × 账本长度`** 的三重乘积（每次 `(agent,回合)` 全量重扫）。**注意：其中"每回合全量重扫"（因子=账本长度）与"每 agent 都扫"（因子=N）是可分离的两个因子**（见 §5）。

## 4. 目标模型（推荐：乙+ 双时钟）——逐条回答任务 7 问

### 4.1 时间语义：**两条时钟，一个账本**

```
【世界结算节拍】 round = 0,1,2,…（不变）
   每回合：P3.5 LIFE(结算) → P4 ARBITRATE(4.1–4.8) → P5 → P6 COMMIT(唯一 append)
   「周/日/时段」= 由 round 派生的【显示口径】，保留（time.py 不变）——供统计/叙事/前端
【个体决策节拍】（新增）
   每 Agent i 维护 due 触发集 W(i)；W(i)≠∅ 时 i 于本轮进入 P2 DECIDE；否则只 T0 记账
```
- **tick 的定义收敛为**：**"世界结算的事件序节拍"**（不是"每个 Agent 的心跳"）。个体节奏由**事件与到期**驱动。
- **事件序 vs 全局时钟**：`seq` 仍是**全局单调、唯一事实序**（红线）；`round` 降级为"**结算/显示的时间标尺**"，仍是所有事件的必带字段。

### 4.2 谁在何时被唤醒：**确定性唤醒集 W1–W6**（落实 `kernel.py:140` 的设想）

| 触发 | 条件（纯函数，可由 `state+log+round` 复算） | 来源事件 |
|---|---|---|
| **W1 到期** | `next_due ≤ round`（计划 slot 到期 / 反思阈值到期 / 周计划） | `SCHEDULE_* / MEMORY_* / derive_time` |
| **W2 来信** | 存在 `MSG_*`，`i∈from/to/members` 且 `round > last_seen` | `MSG_*` |
| **W3 状态** | `status∈{warning,near_death}` 或 needs 越阈 | `STATE_CHANGE / NEED_UPDATE` |
| **W4 市场** | `i` 挂单成交/定向要约到达 | `MARKET_TRADE / OFFER_*` |
| **W5 债务** | `i` 的 `LOAN_*` 到期/逾期 | `LOAN_*` |
| **W6 共处** | `i` 所在场所本轮有他人显著行动 | `PLACE_* / ACTIVITY_*` |

> **U2 已定（Leader 2026-10-12）**：**唤醒集默认含 W6 共处**（最高频人际触发，语义上即现有 `RELATION_ENCOUNTER`），**并提供开关 `wake.triggers.W6`**（可消融）；无需再问。

- 唤醒集 `W(round)=∪_i W(i)` 是 `(state,log,round)` 的**纯函数** → **落日志、可离线复算、可审计**。
- **未唤醒的 Agent**：本轮**不进 P2**，**仍受 P3.5/P4 的被动系统结算**（代谢/税/判死等**继续每回合**，口径不变）。

### 4.3 一致性：**不能让 Agent 看到"未来"**

- **观察窗口 = 闭区间 `(last_acked_seq, cur_seq]`**：`cur_seq` = **做出唤醒决策那一刻**已提交（P6）的最大 `seq`。
- **规则**：① 所有可见事件必须 `seq ≤ cur_seq` 且**已 commit**；② 未提交（本轮缓冲）事件**不可见**；③ 同 `round` 内按 `seq` 全序，**不按"发生先后"猜测**（沿用现状 `perceive.visible_events` 的 `upto_round` 闭区间语义，改为 `upto_seq`）。
- **并发下**：DECIDE 可并发（LLM 调用），但**"读到的世界"= 上一 P6 的快照**（读写分离），**写仍串行**→ **不会读到他人的本轮未提交变更**（天然防"未来"）。

### 4.4 与内核的关系：**回合缓冲 + P6 唯一 append 怎么办**

- **保留**：`run_round` 六阶段 + `arbiter.discard()` 回合缓冲 + **P6 唯一 append + 守恒回滚**（红线）。
- **新增（加法）**：在 **P0 ROUTE** 落实**唤醒集计算**；在 **P2 DECIDE** 落实**门控**（只对 `W(i)≠∅` 的 Agent `step()`）；在 **P1 PERCEIVE** 用**增量视图**替代全量重扫。
- **并发边界**：**并行的是"计算（LLM 调用）"，不是"提交"**（`scale-50-efficiency.md §7-M4 红线`）。`seq` 仍全局全序。
- **D1（放开逐位复现）**给了调度自由度（`n50-m4-probe.md`/Fork B），但**全量日志可审计**保留：唤醒集/到期/跳过**全部落事件**（可审计、可消融）。

### 4.5 对观测/叙事的影响

- **事件顺序**：`seq` 全局全序不变 → 事件卡/编年史/回放**不受影响**。
- **基于"回合"的指标**：`derive_time(round)` 保留 → **按时段/日/周切片口径不变**。
- **新增事件**（走 08 登记，**交 T8**）：`WAKE`（唤醒原因 W1–W6）、`DUE`（到期调度）、`SLEEP`/`IDLE`（未唤醒，可选汇总为一条/回合）、`PERCEPTION_INDEX`（审计增量索引一致性）。**新键进 `engine_version` 指纹**。
- **叙事/世界导演**：不受影响（世界导演事件走世界层，与个体节拍正交）。

### 4.6 迁移代价

| 项 | 结论 |
|---|---|
| 84 回合=1 周 | **不变**（结算节拍保留） |
| 现有口径（经济/生命周期/统计） | **不变**（P3.5/P4/P6 不动） |
| DECIDE | **加法门控**（行为变更 → 需消融对照 + 重冻基线 T236） |
| 感知 | **改增量**（须差分测试证"≡全量"，防假绿） |
| `state_hash`/canonical | 会变（行为变更）→ **重跑 canonical + 重冻**（T236 已在待办） |
| 配置 | 新增 `wake.enabled` / `wake.triggers` / `perception.incremental` 等（进指纹） |

### 4.7 量化对比（**必交付**）

**共同锚点**（T254/scale-50）：`visible_events` 重扫 ≈ `O(N²·rounds²)`；它=**#1 CPU 热点**；IO≈0；N=20×24 → 11.2M `_visible`。

**算式（可独立复算）**：设总感知扫描 `S ≈ N × rounds × L̄`，其中 `L̄` =平均账本长 ∝ `N·rounds`。用 N=20×24 基准反解：
`L̄(20,24) = 11.2M / (20×24) ≈ 23,333`；则 **`S(N,R) ≈ 23,333 × (N/20) × (R/24) × N × R`**（即 `∝ N²R²`）。
外推 **N=50, R=84**：`S ≈ 11.2M × (50/20)² × (84/24)² ≈ 11.2M × 6.25 × 12.25 ≈ 8.6×10⁸` 次 `_visible`（**≈ ×77**）。

| 方案 | N=50×84 感知扫描（外推，**待实测复核**） | LLM 调用/周 | 墙钟 | 失真 | 备注 |
|---|---|---|---|---|---|
| **甲·不改** | **~8.6×10⁸**（基准 100%） | 12k–42.5k / 1.6–3.1M tok | 单核跑不完（>60min，T223） | 0 | 现状 |
| **乙·仅唤醒** | ~（唤醒率 f）×8.6e8（**N 大时 f→1，收益小**） | ≈基线 | 并发可削峰 | 小 | 语义拟人 |
| **乙+·增量感知(c2)** | **↓ ~N 倍** → **~1.7×10⁷**（**~2%**） | ≈基线 | 显著↓ | **0（输出逐字节不变）** | **c2 已批·首选** |
| **丙·异步** | ≈乙+ | 略降 | 更平 | 中 | 复杂度高 |
| **丁·连续** | 同乙+（需重建） | 同量级 | 最平 | **大** | 内核重写 |

> ⚠️ **两条诚实声明**：① 上表 **N=50 列是外推**（基于 N=20 实测 + `∝N²R²` 假设），**标【未验证】**，须复探；② **"乙+ 的 ~N 倍"是"去掉每 agent 重扫"的理论因子**（把 `N×L̄` 降为 `L̄`+索引查），**须以差分/压测确认**。
> **结论**：**CPU 的大头靠"增量感知"（不改 tick）解决；"事件驱动唤醒"提供语义与并发价值，但其 CPU 边际收益在 N 大时有限**。→ **别把"改时间模型"当成 R1 的唯一解**。

## 5. R1 多因归属（**时间模型是必要非充分**）

| R1 根因 | 量级 | 本设计（乙+）能治吗 | 归属 |
|---|---|---|---|
| **CPU 感知重扫 O(N²·rounds²)** | **实测 #1 热点** | ✅（**靠增量感知 c2，非靠改 tick**） | 本设计 + T254 c2 |
| **judge/importance 超线性 O(N^2.1)** | token 大头 | ❌（属感知范围/触发门槛） | M2b / M2 / M1 |
| **side inode ~299k 文件** | 症状 | ❌ 无关 | T228 / T229 |
| **RSS +5MB/回合无界累积** | R8（OOM） | ⚠️ 间接 | 单独定位 |
| **同回合 N 决策尖峰** | 墙钟/并发 | ✅ 乙/丙 | 本设计 |

> **诚实结论**：**"改时间模型就根治 R1"是错的**；正解是 **c2 增量感知（CPU）+ M2b（judge）+ T228（side）** 三管齐下，**时间模型（乙+）解决"尖峰 + 语义拟人"**。

## 6. 推荐与风险

**推荐（供用户/Leader 裁决，非既成）**
1. **P0（先做，最省，已批）**：**c2 增量/每回合索引一次可见性** + c1 共享源事件指针 + c3 流动性 memo + c4 observation 不逐写文件 —— **不动 tick 语义，输出逐字节不变**。
2. **P1（本设计主体）**：**乙+ 双时钟** —— 落实 **P0 ROUTE 唤醒集（W1–W6）+ P2 门控 + P1 增量视图**；并发仅用于 LLM 调用，**提交串行**。
3. **P2（谨慎）**：**丙·个体独立时钟**（异步分时对话，用户目标#1）—— 在 P1 稳定、有实测后评估。
4. **不做（本阶段）**：**丁·连续时间**（与结算/审计/统计冲突，非 R1 解）。

**风险**
- **唤醒集不当 → 漏观察/漏互动**（尤其 W6 共处）→ 须**消融对照**度量失真，勿静默。
- **增量感知 ≠ 全量**（边界/顺序错）→ **差分测试门禁**（防假绿）。**已实证为硬门禁（T264 步骤1）**：机器路上其实有**三份** `visible_events`（`engine/perceive.py` / `life/visibility.py` / `KernelAdapter.perceive` 内联）**且互不等价**（`OFFER_CREATED` 的 `to` 分档仅 engine 有→定向要约"感知得到、记忆不到"；`subject`/`members`-`actor` 语义亦异）。
  → **永久门禁表述（Leader 采纳）**：**同一 records 下，`KernelAdapter.perceive` 的 visible 与 `life.visibility.visible_events` 的输出必须逐条一致（含顺序）**。此门禁**同时**防"增量≠全量"的假绿 **与** "三份实现漂移"。单一真源收敛见 08 §3.5。
- **行为变更 → canonical 基线失效** → 与 T236 重冻联动。
- **未实测项**（§7）**不得当结论引用**。
