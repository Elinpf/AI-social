# 50+ AI 人口 · 效率技术方案（可立项拆解）

> 目标：把「50 个 agent 实时跑起来、成本可预测」拆成**可独立交付的模块**，每条带**量化目标 + 验收判据 + 依赖**。
> 数据来源：**真 LLM 实测基线** `v2/evidence/run_t136_real_llm_canon_n20.jsonl`（sha `0adfe61`，provider `openai_compat`，N=20×84）。
> **所有外推均附假设与算式，可独立复算**（§10 给复算脚本）。**未经验证处标「未验证」。**

---

## 0. 结论摘要（TL;DR）
1. **基线**：N=20×84（1 个仿真周）= **3781.6 s 墙钟、4814 次调用、660,501 tokens**，缓存命中 **65.3%**。折算 **每 agent-回合 2.865 次调用 / 393.2 tokens**。
2. **成本外推 N=50（线性）**：**12,035 次调用 / 1.65M tokens / 仿真周**；墙钟（**串行**）**≈9454 s ≈ 2.63 h**。增长曲线**近似线性**（因绝大多数调用是「每 agent」的）。
3. **真正的瓶颈 = `judge`**：仅 **1010 次调用却吃掉 72.7% 的 token（479,927）**、单次 475 tokens、**thinking=T2、零缓存**。**控 50 规模成本 = 控 `judge`**（若 judge 随关系事件超线性，N=50 token/周上界到 **3.45M**，见 §2）。
4. **最高性价比三招**（按预计省 token 排序）：① **judge 治理**（降频/候选枚举/输出限长，省 ~40–60% 总 token）；② **观察去重缓存**（`importance` 已 93% 命中，可推广到 `dialogue`/`reflect`）；③ **模型分级**（T1 用便宜模型）。
5. **50 规模不需要分布式**：单机足够（负载是**LLM-IO 受限**而非 CPU/内存受限，见 §8）。

## 1. 基线实测（含算式）
**输入**：`N=20`、`rounds=84`（=7 天 × 12 回合/天，即 1 仿真周）、wall `T=3781.6 s`、调用 `C=4814`、token `K=660,501`（in 231,001 / out 429,500）。

| 派生量 | 算式 | 值 |
|---|---|---|
| agent-回合数 | `N×rounds = 20×84` | 1680 |
| 每 agent-回合 调用 | `C/(N×rounds) = 4814/1680` | **2.865** |
| 每 agent-回合 token | `K/(N×rounds) = 660501/1680` | **393.16** |
| 每 agent-周 调用 / token | `C/N` / `K/N` | 240.7 / **33,025** |
| 每仿真回合 调用 / token | `C/rounds` / `K/rounds` | 57.31 / 7,863 |
| 平均 token/调用 | `K/C` | 137.2 |
| 缓存命中率 | `cached/C = 3143/4814` | **65.3%** |
| 墙钟/调用（含非 LLM 开销） | `T/C` | 0.785 s |

**按 purpose 拆解**（复算：见 §10）：
| purpose | 调用 | 缓存% | tok_in | tok_out | tok_total | 占比 | tok/调用 | tier |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| **judge** | 1010 | **0%** | 135,680 | 344,247 | **479,927** | **72.7%** | 475.2 | T2(thinking) |
| reflect | 140 | 10% | 55,296 | 9,335 | 64,631 | 9.8% | 461.6 | T1 |
| importance | 3234 | **93%** | 3,757 | 56,130 | 59,887 | 9.1% | 18.5 | T1 |
| dialogue | 270 | 8% | 28,363 | 8,989 | 37,352 | 5.7% | 138.3 | T1 |
| describe | 20 | 0% | 3,675 | 8,319 | 11,994 | 1.8% | 599.7 | T1 |
| plan | 20 | 0% | 1,825 | 1,656 | 3,481 | 0.5% | 174.1 | T1 |
| negotiation | 120 | 83% | 2,405 | 824 | 3,229 | 0.5% | 26.9 | T1 |

> **关键读数**：`judge` 用 21% 的调用占 **72.7% 的 token**；`importance` 用 67% 的调用只占 9%（因为 93% 命中缓存）。**cost 不在「调用多」，在「judge 的 thinking 输出长」。**

**每 purpose 的规模律（决定外推曲线）**：
| purpose | 触发频率（源码事实） | 随 N 的律 |
|---|---|---|
| plan / describe | 每 agent 每**周**各 1 次（20/20） | 线性 N |
| reflect | 每 agent 每**天** 1 次（140 = 20×7） | 线性 N |
| negotiation | 每 agent 每**天** ~1 次（120 = 20×6） | 线性 N |
| dialogue | 每 agent 每**天** ~2 次（270） | 线性 N |
| importance | 每 agent 每**回合** ~1.93 次（3234） | 线性 N |
| **judge** | 按**关系事件/（peer,周）**触发，部分维度 **cap 4 peers/agent/周**（`llm_judgment_by_dimension`：affection178/affinity40/familiarity412/trust4/respect178/stance178/weekly_focus20） | **≥线性**；上界近似随**关系对** → 最坏 O(N²)（有 cap） |

## 2. 成本外推：N=20 → N=50（含算式）
**假设 A1**：保持 84 回合/周、每 agent 的调用频次与 N=20 相同（即各 purpose 的 per-agent 速率不变）→ **线性缩放**，`s = 50/20 = 2.5`。
**假设 A2**：`judge` 的关系事件量按最坏估计可随关系对增长 → 给**线性**与**二次**两条边界。
**假设 A3**：token/调用的均值按 N=20 实测（不因 N 变化）——若上下文随人口膨胀则需要 §4-压缩，届时**另行标定**。

| 量 | 算式 | 线性(s=2.5) | 二次上界(judge×6.25) |
|---|---|---|---|
| 调用 / 仿真周 | `C×s` | **12,035** | 12,035 |
| token / 仿真周 | `K×s`(线性) / `479927×s² + 180574×s`(二次) | **1,651,252 (1.65M)** | **3,450,979 (3.45M)** |
| token / 仿真日 | `(周值)×12/84` | **235,893** | **492,997** |
| token / 小时（真墙钟，串行） | `周值 / (T×s/3600)` | **628,782 /h**（速率不变） | — |
| 墙钟 / 仿真周（**串行**） | `T×s` | **9454 s = 2.63 h** | 2.63 h+ |
| 墙钟 / 仿真周（并发度 K_c） | `T×s/K_c` | `9454/K_c` | — |

> 二次上界算式：`judge 479,927 × (50/20)² = 2,999,544` ＋ `非-judge 180,574 × (50/20) = 451,435` = **3,450,979**（≈3.45M）。
> 即 **N=50 的 token/周落在 [1.65M, 3.45M] 区间**，取决于 judge 触发律（线性还是随关系对）。

**增长曲线判定**：
- **调用数 = 线性**（每个 agent 的固定节奏调用为主）。
- **token = 近线性，但 `judge` 是超线性风险点**：N=50 时 judge 要么仍线性（若关系事件不随人口爆炸）→ 1.2M；要么二次 → 3.0M。**差 2.5 倍，全看 judge 触发律。**
- **瓶颈**：① **judge 的 thinking 输出 token**（当前 72.7%）；② **wall-clock（若串行）**；③ 瞬时**并发尖峰**（同回合 N 个 decide）。

**每小时/每天量级**：
- **仿真时间**：N=50 线性 → **~0.24M token/仿真日**、**1.65M token/仿真周**。
- **真墙钟**：串行速率 ~**63 万 token/h** 恒定（线性缩放不改变速率，只拉长墙钟）。要「实时感」（1 仿真周 ≲ 1 真小时），N=50 需并发度 `K_c≈2.5`（见 §3）。

## 3. 分时 / 异步调度
**问题**：现架构是**回合内按 agent 顺序步进**（串行），N=20 时 1 回合 ≈ 45 s（`3781.6/84`）。N=50 串行 → 回合 ~112 s、仿真周 2.63 h。若简单改成「同回合全部并发」，会产生 **N 个并发 LLM 调用的尖峰**。

**候选模型**：
| 模型 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 回合内并发 gather | 每回合 `asyncio.gather` 全 agent decide | 简单、墙钟↓ | 尖峰 = N；无背压 |
| B 错峰（staggered） | 回合窗口内按 `hash(agent_id)` 把 agent 决策摊到 K 个槽 | 削尖峰、平滑 QPS | 需回合窗口可拉长 |
| C 令牌桶 + 后台持续 | agent 各自后台循环，全局 `token_bucket` 限速 | 平滑、天然背压 | 需重构决策为「非回合对齐」（**未验证**是否与确定性内核兼容） |
| D 关键路径优先 | 只对**判据相关**决策（成交/社交）并发，`judge`/`reflect` 走低优先队列 | 保实时 + 压成本 | 需优先级标注 |

**推荐：B + D 组合（保守，不改内核语义）**
- **回合内**：`decide` 阶段对 agent 做 `asyncio.gather`，但用 **bounded semaphore** 限并发 `Kc`；**按 `hash(agent_id)` 决定启动偏移**，摊到 `Kc` 个时隙 → 峰值并发 = `Kc` 而非 N。
- **低优先队列**：`judge`/`reflect`/`describe`（F 类、非判据）进后台队列，**可延迟到回合末或空闲窗口**，不阻塞 `decide` 关键路径。
- **全局令牌桶**：`min(Kc, provider 限流)` 个许可/秒；超额 → 排队而非丢弃（可观测，见 §5）。
- **验收判据**：N=50 时**峰值并发 ≤ Kc**（仪表可测）、**1 仿真周墙钟 ≤ 1.5 h**（Kc=4，串行 2.63h/4≈0.66h，留余量）、**决策顺序仍确定性**（replay parity 不变，见 §10 红线）。

## 5. 降级与预算（**必须可观测**）
**预算（提案值，可调）**：
- `daily_token_budget`：例如 **3M token/仿真日**（N=50 线性 0.24M/日，留 ~12× 余量给真 LLM 抖动）。
- `max_concurrency Kc`：例如 **8**（provider 限流之下）。
- `judge_daily_cap`：例如 **≤1500 次/仿真日**（基线 1010/周 的外推 2.5×=2525/周≈360/日；设 cap 留治理空间）。

**降级阶梯（超额时按序触发，每级打旗标）**：
| 级 | 触发 | 动作 | 观测旗标 |
|---|---|---|---|
| L0 | 正常 | — | — |
| L1 | 预算 > 80% | `judge` 降频（低价值维度抽样 1/2） | `DEGRADE{level:1,rule:judge_sample}` |
| L2 | 预算 > 100% | `describe`/`reflect`/`negotiation` 降模型到 T1-mini | `DEGRADE{level:2,rule:model_downgrade}` |
| L3 | 硬上限 | 只保**判据关键决策**（成交/社交/生死），其余**跳过** | `DEGRADE{level:3,rule:critical_only}` |
**红线**：**任一降级必须落一条可观测事件**（`DEGRADE`/`LLM_CALL.degraded=true`），**禁止静默变差**；评测报告须统计各级发生次数。

**验收判据**：注入超额流量 → 触发 L1–L3 → 看板 `degrade_events` 分列非零、且**结论指标被标记为「降级态」**（不得混入正常证据）。

## 8. 明确**不需要**的（给理由）
| 环节 | 结论 | 理由 |
|---|---|---|
| **分布式多机** | **不需要** | 负载是 **LLM-IO 受限**：单机 CPU/内存占用极低（N=20 run 纯计算远小于 LLM 等待）；N=50 串行仅 2.6h，并发后 ~0.7h。加机器不解决瓶颈（瓶颈在 provider 延迟与 token 预算）。 |
| **自研推理服务/本地大模型** | **暂不需要** | provider 已满足；自建只在「token 预算不可控」时才值得（**未验证** 成本拐点） |
| **复杂消息队列/Kafka** | **不需要** | 单进程 asyncio 队列足够；引入 MQ 徒增运维 |
| **token 级 streaming 优化** | **不需要（先）** | 不是瓶颈；先做 M2/M1 |
| **数据库分库分表** | **不需要** | 状态是单进程内存 + 日志；50 规模无此压力 |

> 若未来 N≥500 或要求「多城镇并行」，再评估分布式；**当前 50 规模纯属过早优化**。

## 9. 假设与不确定性（**未验证项**）
- **A1/A3**：per-agent 调用频次与 token/调用在 N=50 保持不变 —— **未验证**（人口↑可能使上下文/关系变多 → 上修）。
- **judge 触发律**：线性 vs 二次 —— **未验证**；决定成本差 2.5×。**必须补一次 N=35/50 的 judge 调用计数实测**再定预算。
- **C 模型（后台持续调度）与确定性内核兼容性** —— **未验证**；推荐先用 B 模型（不改内核）。
- provider 是否支持 **batch / 前缀缓存** —— **未验证**；影响 §4.6/4.7 收益。
- 降级阈值（80%/100%）为**提案值**，需在真跑中校准。

## 10. 复算脚本（独立可验）
```bash
cd code
python - <<'PY'
import json, collections
recs=[json.loads(l) for l in open('../v2/evidence/run_t136_real_llm_canon_n20.jsonl',encoding='utf-8')]
calls=[r for r in recs if r['type']=='LLM_CALL']

PY
```
