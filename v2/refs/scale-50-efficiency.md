# 50+ AI 人口 · 效率技术方案（可立项拆解）

> 目标：把「50 个 agent 实时跑起来、成本可预测」拆成**可独立交付的模块**，每条带**量化目标 + 验收判据 + 依赖**。
> 数据来源：**真 LLM 实测基线** `v2/evidence/run_t136_real_llm_canon_n20.jsonl`（sha `0adfe61`，provider `openai_compat`，N=20×84）。
> **所有外推均附假设与算式，可独立复算**（§10 给复算脚本）。**未经验证处标「未验证」。**

---

## 0. 结论摘要（TL;DR）
1. **基线**：N=20×84（1 个仿真周）= **3781.6 s 墙钟、4814 次调用、660,501 tokens**，缓存命中 **65.3%**。折算 **每 agent-回合 2.865 次调用 / 393.2 tokens**。
2. **成本外推 N=50 = 超线性（≈O(N²)，非线性）**：由**已有日志实测**（N=10 vs N=20，见 §2）得到缩放指数——**固定节奏 purpose 严格线性（指数 1.00）**，**事件触发 purpose 超线性**（`importance` 指数 **2.64**、`judge` **1.64**），**总指数 ≈ 2.10**。
   → N=50 区间：**12,065 次调用 / 1.63M tokens（线性下界）** ～ **42,560 次调用 / 3.10M tokens（超线性拟合）** / 仿真周；串行墙钟 **2.6 h ～ 9.3 h**。
3. **真正的瓶颈 = `judge`**：仅 **1010 次调用却吃掉 72.7% 的 token（479,927）**、单次 475 tokens、输出 344k、**零缓存**。**控成本 ≠ 关 thinking**（thinking 是用户有意保留的设计）；真杠杆在 **降触发率 + 压输出 + 缓存**（见 §4-M2）。
4. **最高性价比**（按预计省 token 排序）：① **`judge`/`importance` 判别式化（M2b）** —— 从**生成**改**受限选择/打分**，judge token **≤0.2×**（最根本；兼容"软判定保留 thinking"，是另一条路）；② **judge 治理（M2）**（降触发率/压输出/缓存）；③ **观察去重缓存（M1）**；④ **模型分级（M3）**。
5. **50 规模不需要分布式**：单机足够（负载是**LLM-IO 受限**而非 CPU/内存受限，见 §8）。

**输入**：`N=20`、`rounds=84`（=7 天 × 12 回合/天，即 1 仿真周）、wall `T=3781.6 s`、调用 `C=4814`、token `K=660,501`（in 231,001 / out 429,500）。

| 每 agent-回合 调用 | `C/(N×rounds) = 4814/1680` | **2.865** |
| 每 agent-回合 token | `K/(N×rounds) = 660501/1680` | **393.16** |
| 每 agent-周 调用 / token | `C/N` / `K/N` | 240.7 / **33,025** |
| 每仿真回合 调用 / token | `C/rounds` / `K/rounds` | 57.31 / 7,863 |

## 2. 成本外推：N=20 → N=50（含算式，**修正为超线性**）
**假设 A1**：各 purpose 的缩放**指数取 §1 实测**（固定节奏 = 1.00；`importance` = 2.64、`judge` = 1.64）。
**假设 A2**：token/调用 取 N=20 **真 LLM** 实测（不随 N 变）；若上下文随人口膨胀需 §4-压缩，届时另行标定。
**算式**：`N=50 调用(purpose) = N20调用(purpose) × (50/20)^指数`；`token = 调用 × token/调用`。

| purpose | N20 调用 | 指数 | **N50 调用** | tok/调用 | **N50 tokens** |
|---|---:|---:|---:|---:|---:|
| judge | 991 | 1.64 | 4,453 | 475.2 | **2,116,273** |
| importance | 3,265 | 2.64 | 36,681 | 18.5 | 678,604 |
| reflect | 140 | 1.0 | 350 | 461.6 | 161,560 |
| dialogue | 270 | 1.0 | 675 | 138.3 | 93,353 |
| describe | 20 | 1.0 | 50 | 599.7 | 29,985 |
| plan | 20 | 1.0 | 50 | 174.1 | 8,705 |
| negotiation | 120 | 1.0 | 300 | 26.9 | 8,070 |
| **合计** | **4,826** | — | **42,560** | — | **3,096,550** |

**对照：线性下界（把所有 purpose 都当指数 1.0）** = 12,065 调用 / **1.63M tokens**。

| 量 | **线性下界** | **超线性拟合（推荐）** |
|---|---|---|
| 调用 / 仿真周 | 12,065 | **42,560** |
| token / 仿真周 | 1.63M | **3.10M** |
| token / 仿真日 | 0.23M | **0.44M** |
| 墙钟 / 仿真周（串行 `0.785s/call`） | 2.63 h | **9.28 h** |
| 墙钟 / 周（并发 K_c） | `2.63h·(call比)/K_c` | `9.28/K_c h` |

**增长曲线判定（修正）**：
- **非线性 —— 经验指数 ≈ 2.10（约 O(N²)）**：固定节奏 purpose 线性，**事件触发的 `importance`（2.64）、`judge`（1.64）超线性**（人口↑→可见事件/关系对↑→触发↑）。
- **`judge` 是最贵的超线性项**：N=50 时单它 **2.12M token/周（68% 总量）**。
- **瓶颈**：① **`judge` 的输出 token**（72.7%，且随人口超线性）；② **wall-clock**（超线性拟合下串行 9.3h）；③ 瞬时**并发尖峰**（同回合 N 个 decide）。

**每小时/每天量级**：
- **仿真时间**：N=50 = **0.44M token/仿真日**、**3.10M token/仿真周**（超线性）；线性下界 0.23M/1.63M。
- **真墙钟**：超线性拟合下 token 速率 **≈ 3.10M / 9.28h ≈ 334k token/h**（**比 N=20 的 629k/h 更低** —— 因为调用数增速快于墙钟，实际单机吞吐会先撞 provider 限流）；要「实时感」（1 仿真周 ≲ 1 真小时）需并发 `K_c ≈ 9`。

> ⚠️ **区间而非点值**：因 `judge` 在 N=20 各 run 间波动大（447–1010），**N=50 token/周 ∈ [1.6M, 3.1M]，取 3.1M 作规划上界**。

## 3. 分时 / 异步调度
**问题**：现架构是**回合内按 agent 顺序步进**（串行），N=20 时 1 回合 ≈ 45 s（`3781.6/84`）。N=50 串行 → 回合 ~112 s、仿真周 2.63 h。若简单改成「同回合全部并发」，会产生 **N 个并发 LLM 调用的尖峰**。

**候选模型**：
| 模型 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 回合内并发 gather | 每回合 `asyncio.gather` 全 agent decide | 简单、墙钟↓ | 尖峰 = N；无背压 |
| B 错峰（staggered） | 回合窗口内按 `hash(agent_id)` 把 agent 决策摊到 K 个槽 | 削尖峰、平滑 QPS | 需回合窗口可拉长 |
| C 令牌桶 + 后台持续 | agent 各自后台循环，全局 `token_bucket` 限速 | 平滑、天然背压 | 需重构决策为「非回合对齐」（**未验证**是否与确定性内核兼容） |
| D 关键路径优先 | 只对**判据相关**决策（成交/社交）并发，`judge`/`reflect` 走低优先队列 | 保实时 + 压成本 | 需优先级标注 |

**推荐：B + D 组合（保守，不改内核语义）**
- **回合内**：`decide` 阶段对 agent 做 `asyncio.gather`，但用 **bounded semaphore** 限并发 `Kc`；**按 `hash(agent_id)` 决定启动偏移**，摊到 `Kc` 个时隙 → 峰值并发 = `Kc` 而非 N。
- **低优先队列**：`judge`/`reflect`/`describe`（F 类、非判据）进后台队列，**可延迟到回合末或空闲窗口**，不阻塞 `decide` 关键路径。
- **全局令牌桶**：`min(Kc, provider 限流)` 个许可/秒；超额 → 排队而非丢弃（可观测，见 §5）。
- **验收判据**：N=50 时**峰值并发 ≤ Kc**（仪表可测）、**1 仿真周墙钟 ≤ 1.5 h**（Kc=4，串行 2.63h/4≈0.66h，留余量）、**决策顺序仍确定性**（replay parity 不变，见 §10 红线）。

### 4.10 M2b · **判别式化（最根本的杠杆）** —— 从「生成」改「受限选择」
> **动机**：`judge` 用**生成式 T2（长 CoT）**产出软判定，单次 ~475 tok（out 344k = 72.7% 总量）。**「在便宜的地方做昂贵生成」是成本结构的根因。**

**改法（参考 jev / 米哈游 deck 的判别式+分层）**：
1. **候选枚举**：把判定表述为**只在合法候选集中选择**（`choice/score/neutral` 三式），**不自由生成文本** → 输出 = 一个标签 + 分数。
2. **类型化 rubric 打分**：按Dimension 逐项 **0–1 打分 + 校准置信度**（共情/人设一致/安全），短 JSON 输出。
3. **Best-of-N + RM 选优**（仅在**必须生成话术**处，如 dialogue 措辞）：生成 N 条 → RM 打分选最优；**判别式打分免费**（jev：单前向、输出不占生成 token）。
4. **分层**：**最高价值维度**保留生成式（含 thinking），其余走判别式 —— 对应米哈游「NPC L1–L5 智能分级」。

**预期收益**：judge token **≤0.2× 基线**（输出从 475 tok/次 → 个位–几十 tok/次）；这是**比 M2 更根本**的降本。

**与用户「软判定保留 thinking」是否兼容？—— 兼容（且是另一条路，非降 thinking）**：
- 用户要的是**软判定的质量**，不是"CoT 文本"本身。**判别式 + 校准置信度**能在**不产长 CoT** 的前提下给出同等软判定。
- 若确需 thinking：**分层保留**（只对 T2 重大决策的**最高价值维度**生成式 thinking，其余判别式）——既守住"软判定保留 thinking"，又砍掉 80% 的生成 token。

**依赖/未验证**：判别式需要 provider 暴露**打分头/logprob**或支持**受限选择**（constrained decoding）—— **未验证** `openai_compat` 是否支持；若不支持，退化方案 = 「受限候选 + 短 JSON 打分」（仍比长 CoT 省 token）。

**⚠️ 校准验收（退化方案的必测项，不能只看省了多少 token）**：
- **动机**：判别式的核心价值在 **ECE 校准过的置信度**（jev 的分类头）。**生成式模型自报的分数校准普遍很差**（"自信地说 0.9 然后错"）；**而置信度正是「回退/降级」的判据** —— 若不可靠，**M2b 的分层与降级阶梯就建在沙子上**。
- **必须实测**：走退化方案时，**实测校准度**（**可靠性图 / ECE**，或至少**分层命中率**：置信档次 → 实际正确率）。
- **裁决规则**：**若校准很差 → M2b 只保留「受限选择」那一半，砍掉「置信度回退」**；回退改用**规则判定**（如**候选间分值差距阈值**）。
  > 原则：**宁可少一个花哨功能，也不要一个会撒谎的信心值**（同我们全路线的"防假绿"）。
- **验收判据**：`ECE ≤ 0.05`（或分层命中率单调）才允许启用置信度回退；否则按上述规则降级为「受限选择 + 规则回退」。

> **三线收敛**：① 我们的 **O(N²)** 实测（judge/importance 超线性）；② emergence-researcher 的 **jev 判别式单前向（输出免费）**；③ 米哈游 deck 的**判别式+Best-of-N+RM+NPC 分层** → **同一句：不要在用得起廉价判别的地方做昂贵生成。**

## 5. 降级与预算（**必须可观测**）
**预算（提案值，可调）**：
- `daily_token_budget`：例如 **3M token/仿真日**（N=50 线性 0.24M/日，留 ~12× 余量给真 LLM 抖动）。
- `max_concurrency Kc`：例如 **8**（provider 限流之下）。
- `judge_daily_cap`：例如 **≤1500 次/仿真日**（基线 1010/周 的外推 2.5×=2525/周≈360/日；设 cap 留治理空间）。

**降级阶梯（超额时按序触发，每级打旗标）**：
| 级 | 触发 | 动作 | 观测旗标 |
|---|---|---|---|
| L0 | 正常 | — | — |
| L1 | 预算 > 80% | `judge` 降频（低价值维度抽样 1/2） | `DEGRADE{level:1,rule:judge_sample}` |
| L2 | 预算 > 100% | `describe`/`reflect`/`negotiation` 降模型到 T1-mini | `DEGRADE{level:2,rule:model_downgrade}` |
| L3 | 硬上限 | 只保**判据关键决策**（成交/社交/生死），其余**跳过** | `DEGRADE{level:3,rule:critical_only}` |
**红线**：**任一降级必须落一条可观测事件**（`DEGRADE`/`LLM_CALL.degraded=true`），**禁止静默变差**；评测报告须统计各级发生次数。

**验收判据**：注入超额流量 → 触发 L1–L3 → 看板 `degrade_events` 分列非零、且**结论指标被标记为「降级态」**（不得混入正常证据）。

## 7. 模块清单（可转任务）
| ID | 模块 | 量化目标 | 验收判据 | 依赖 |
|---|---|---|---|---|
| **M1** | 观察去重/缓存扩展 | 非-judge 缓存命中 ≥90% | 看板 cache_hit（purpose）≥90%；结论不变 | — |

> ① **回合边界强同步**（必须等全体 agent 完成本回合才进下一回合）→ 放开后可改**自由推进**；

## 8. 明确**不需要**的（给理由）
| 环节 | 结论 | 理由 |
|---|---|---|
| **分布式多机** | **不需要** | 负载是 **LLM-IO 受限**：单机 CPU/内存占用极低（N=20 run 纯计算远小于 LLM 等待）；N=50 串行仅 2.6h，并发后 ~0.7h。加机器不解决瓶颈（瓶颈在 provider 延迟与 token 预算）。 |
| **自研推理服务/本地大模型** | **暂不需要** | provider 已满足；自建只在「token 预算不可控」时才值得（**未验证** 成本拐点） |
| **复杂消息队列/Kafka** | **不需要** | 单进程 asyncio 队列足够；引入 MQ 徒增运维 |
| **token 级 streaming 优化** | **不需要（先）** | 不是瓶颈；先做 M2/M1 |
| **数据库分库分表** | **不需要** | 状态是单进程内存 + 日志；50 规模无此压力 |

> 若未来 N≥500 或要求「多城镇并行」，再评估分布式；**当前 50 规模纯属过早优化**。

## 9. 假设与不确定性（**未验证项**）
- **A1/A3**：per-agent 调用频次与 token/调用在 N=50 保持不变 —— **未验证**（人口↑可能使上下文/关系变多 → 上修）。
- **judge/importance 缩放指数**：**已用现有日志估出**（judge 1.64 / importance 2.64 / 总 2.10，§1），**但含混淆**（N=10 点来自不同 run 家族、judge 在 N=20 各 run 间 447–1010 波动）。**建议补一次「同版本 N=10 & N=35」的 judge 计数**再定死预算。
- **thinking 是否降级**：**待用户裁决**（用户有意保留 T2 thinking）→ M2 默认不动它。
- **C 模型（后台持续调度）与确定性内核兼容性** —— **未验证**；推荐先用 B 模型（不改内核）。
- provider 是否支持 **batch / 前缀缓存** —— **未验证**；影响 §4.6/4.7 收益。
- 降级阈值（80%/100%）为**提案值**，需在真跑中校准。
