# D9c 预登记：`reply_pick_target` 的挑选顺序（最近优先 → 最久优先）

> 立此件：Leader（team-leader）｜2026-10-29
> 上游断点：`v2/evidence/d9b_reply_window_on_A1_base_result.md` §6 —— **窗口长度不是瓶颈，瓶颈是挑选顺序**
> 起跑前置：需先实现开关（`HITT_REPLY_PICK_ORDER`，默认 = 现状）；本件批准**实现 + mock 验证**，**不批准跑真 LLM 批**

## 0. 为什么做这个（D9b 留下的唯一线索）

D9b 实测：`reply_window_rounds` 2→4 **零行为差异**，`lag` 分布两臂同为 `{1: 656, 2: 7}`、`lag≥3 = 0`。
代码定位（`code/life/agent.py:1048` `_pick_reply_target`）：

```python
for ev in reversed(list(wv.visible_events)):   # 最近优先
    ...
    if fallback is None:
        fallback = ev                          # 取第一条满足的 = 最新的
```

⇒ **只要还存在一条 lag=1 的未回入站，agent 永远不会去接更旧的那条**（旧消息被"饿死"，直到超窗作废）。
⇒ 窗放宽不改变任何事（D9b 已证），因为**被饿死的不是"超窗的"，而是"被更新的抢先的"**。

## 1. 单变量与固定参数

| 项 | 值 |
|---|---|
| 受检变量 | `life_v2.dialogue.reply_pick_order` ∈ {**`recent_first`（H0 = 现状）**, **`oldest_first`（H1）**} |
| 注入方式 | 运行时 `life_v2` override（同 D9b：`GIT_INDEX_FILE` 无关；`life/config.set_override` 注入，**不落盘、不改文件指纹**） |
| **两臂固定** | `reply_window_rounds = 4`（**两臂都用默认 4**，故 window 不是本批变量；D9b 已证 2 与 4 在 `recent_first` 下等价） |
| 其余固定 | `seed=42 / agents=16 / rounds=84 / max_turns=6 / max_slots=2 / max_turns_per_round=2 / provider=mock` |
| 基座代码 | A1-回复预算基座（`HITT_REPLY_BUDGET=1`），`HITT_NO_INIT_UNREPLIED` 不设 |

**实现硬约束（实现者必须做到，做不到即验收不通过）**：
1. **默认 `recent_first` 路径与现状逐字节等价**：开关关闭时不改变任何挑选结果。验证方式：用同参重跑一臂，与 `mock_d9b_rw4_treat_…/run.jsonl` 的 **`MSG_*` 事件逐条 payload 比对 0 差异**（hash 链与 `config_digest` 允许不同）。
2. `oldest_first` 只改**遍历方向**，**不得改动任何硬条件**（可见性 / 未超时 / 未到轮数顶 / 未重复回 / K 上限 / `prefer_threads` 优先）。
3. `prefer_threads`（旧账优先）**仍然最高优先**，与新旧顺序正交——不得因为改方向而削弱它。

## 2. 必报量（**每条都带 H0 取值**，按 `v2/refs/hit-metric-h0-baseline-rule.md`）

| # | 量 | H0（recent_first）实测 | H1 下能否离开 | 区分力 |
|---|---|---|---|---|
| 1 | **`lag ≥ 3` 的回复条数** | **0** | **能**（顺序改了就可能出现） | ✅ **主判据** |
| 2 | `lag` 分布（逐项） | `{1: 656, 2: 7}` | 能 | ✅ |
| 3 | `lag` 的 mean / p90 / max | 1.0106 / 1 / 2 | 能 | ✅ |
| 4 | **`starved_inbound`：从未被回复的入站消息数** | 需本批实测（H0 臂即基线） | 能（饿死应减少） | ✅ |
| 5 | MSG 总数 / 发起 / 回复 / 线程数 | 929 / 266 / 663 / 266 | 能 | ✅ |
| 6 | **≥3 轮绝对条数**（分母 266 线程） | **120** | 能 | ✅ |
| 7 | ~~`lag ≤ window` 覆盖率~~ | ~~恒 100%~~ | **不能**（`window=4` 下 `lag≤2` 恒真） | ❌ **空转，禁用** |

> 第 7 项按新纪律**明令禁止引用**；它的"100%"由 lag 上界决定，与两臂差异无关。

## 3. 判定四档（**按特异性排序，命中即停**）

| 序 | 档位 | 条件（全部成立） |
|---|---|---|
| 1 | **E-有效** | `lag≥3 条数 > 0` **且** `≥3 轮绝对条数 ≥ 120` **且** `MSG ≥ 836`（= 929×0.90） |
| 2 | **L-仅滞后·无收益** | `lag≥3 条数 > 0` **但** `≥3 轮绝对条数 < 120` |
| 3 | **T-不可判（机制未触达）** | `lag` 分布与 H0 **逐项相同** **且** 两臂 `MSG_*` 事件逐条比对 **0 差异** |
| 4 | **I-无效（结构量不变）** | 以上均不命中，且所有结构量相对 H0 变动 ≤ 2% |

- 命中 2 ⇒ 必须写「**用拖延换滞后**」，**不得**写成"提高了真实感"。
- 命中 3 ⇒ 只许写「不可判（机制未触达）」，**禁止**写「无效」。
- 命中 1 ⇒ 也只许写「**结构上首次出现跨 3 轮以上的接话**」，**不得**外推为"更像真人"——那是语言侧问题，mock 答不了。

## 4. 三条反事实（各须给数值）

1. **若 `lag≥3` 仍 = 0** ⇒ 顺序**也不是**瓶颈。此时必须补一条**解释性量**：`starved_inbound` 若也几乎为 0，说明"根本没有积压"（每条入站都被及时接了）⇒ 该方向整条作废，不再试。
2. **若 `lag` 变大但 `≥3 轮绝对条数 < 120`** ⇒ 只是把"立刻接"换成"晚点接"，对话没有变长 ⇒ 判 L，不报为改进。
3. **若 MSG 总数 < 836** ⇒ 用**少说话**换滞后，与"生活气息"方向相反（人不会因为要显得自然就少说话）⇒ 直接判否，不看其他指标。

## 5. 局限（写死在件头，随结论一起引）

1. **mock 无语言生成** ⇒ 本批只能说"接话的**时间分布**变了"，**不能**说"对话读起来更像真人"。语言侧必须真 LLM 批另答。
2. **"隔几轮才回"本身不是目的**：真人拖着回话常伴随"忘了→忽然想起""忙着→事后补一句"这类**内容特征**（如"哎我刚才没顾上"）。若只改顺序、生成侧不体现"迟到的歉意/补白"，可能只是**让对话变慢**，不是变真。**这一条是本方向最大的风险，实现后必须人工读样本判断**。
3. 单 seed、单臂各一次；mock 确定性下不需重复，但跨 seed 未验。
4. 本批**不涉及** `window`：若 `oldest_first` 下出现 `lag≥5`，说明窗口 4 开始成为约束——那是**后续**批的变量，本批只记录该现象，不据此改判。
