# 备忘：批准 ≠ 可以跑（起跑前必须重新验环境）

> 来源：2026-10-23 leader 与 prompt-linguist 各自犯过一次同类错误后确立。

## 铁律

**「方案批准」与「现在可以起跑」是两个时刻。中间必须再做一次环境确认。**

- 批准只代表**方案通过**（判据合理、变量单、成本可接受）；
- **是否能起跑**取决于**当下机器状态**：有无他人批在跑、有无遗留进程、是否有人在跑测试/渲染。

## 起跑前三件（逐条打勾，不许用 `pgrep | head` 代替）

1. **逐条列进程**：`ps -eo pid,lstart,cmd | grep "[o]rchetration run"`（注意字符类避免自匹配），**每条都看 cmdline**，不要只看数量；
2. **抽 3 条 `LLM_CALL` 看 `provider`**：确认真跑（`openai_compat`），不是 mock 回退；
3. **看别人的批是否收尾**：**看产物 + 日志尾部**（`meta.json` 是否出现、`TURN_SEAL` 是否到最后回合），**不看 cgroup、不看文件时间戳**（flush 缓冲会骗人）。

## 反面案例（本轮真实发生）

- 我（prompt-linguist）：PM 看 `run.jsonl` 停在 2,629 行、无 `meta.json`，判"第五次失败"，实际 pid 811089 正在跑；
- leader：同日"批准今夜跑 D12-C"时未先查环境，实际 `run_f6off_cycle06`（n16×84）正在跑。

## 连带规则

- **宁可明早跑，不要并行**：并行会污染两边的速率读数（本轮 A0 的 0.75→3.0 分钟/轮 已被怀疑受此影响）。
- 起跑前在频道报「起跑 + 预计分钟」，并在起跑后 60 秒内报一次硬闸结果。
