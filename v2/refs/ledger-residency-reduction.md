## 0. 结论速览

1. **【事实】主项确认**：`ledger.records` 全量常驻是已归因里的最大单项（T272：**3.065 MB/回合**，占已归因 78.9%，本身超线性 ~1.9×）。N=20×84 共 **130,323 事件**（磁盘 JSONL 57.7 MB）。
2. **【事实】未定位 54%：本轮只做到"部分归位"，如实标注**（不凑）：
   - 本轮只读补测发现，增长最快的**剩余类别是 `builtins.set`**（R=24：8.39→16.78 MB，**≈+0.59 MB/回合**），且**这些 set 大多可达自 `engine.state` 图**（并入 state，非独立结构）。
   - 但 **`sys.getsizeof` 深遍历"方法敏感"**：同一 R=24/seed7 下 `engine.state` 深尺寸在两次测量中为 **36.6 MB vs 69.8 MB**（见 §2.3）→ **state 的精确份额不能据此下结论**，**残差（解释器/分配器/方法误差）仍未能精确拆开**。
3. **【事实】N=50×84 账本常驻上界**：按事件数 O(N²)~×6 外推 → **~1.4–1.9 GB（仅账本）**，加 state 侧 → **数 GB** → 与 R8 的 OOM（anon-rss 23.2GB）方向一致。**（带假设，见 §3）**
4. **【建议】削减方案**：**分段/流式落盘**（同 T262 flush 思路）+ **只保留"可重建的轻索引"**（`seq→{round,type,offset,len}`）；`state.event_index` 同法轻量化；`observed/seen` 类集合改**可由日志重建**。**纯存储层，不动语义**。
5. **【建议】代价**：**降内存换磁盘 IO / 时间**（量级见 §5.3）；**不是免费**。

## 4. 削减方案（**【建议】**，纯存储层）

### 4.1 核心：`ledger.records` 由"全量在内存"→"**尾段常驻 + 已落盘段只读**"

- **分段（segment）**：每 `SEG_ROUNDS` 回合（**建议默认 12**，与 T262 `--flush-every 12` 对齐）把该段事件**原子落盘**为一个段文件（沿用 T262 的 temp+`os.replace`）。
- **常驻**：内存只保留**当前尾段**（`≤ SEG_ROUNDS` 回合的事件）。**已封段从内存释放**。
- **读取**：需要历史事件时，经索引从段文件按偏移读回（只读、可缓存 LRU）。

### 4.2 只保留"**可重建的轻索引**"

- **`seq → {round, type, phase, actor, offset, len}`**（定长/紧凑），替代"整条 record 常驻"。TURN_SEAL/链哈希**照旧**（哈希链**本身**不要求全量常驻：链条只需 `prev_hash` 链式，段文件保存 record 与 hash）。
- **`state.event_index`**（现在 `seq→整条 record`，与 `ledger.records` **共享同一批 dict**）→ 同步改为**轻索引**（否则等于没省）。
- **`state.observed` / 每 agent `observed_event_seqs` / life `_observed_seqs`**：**改为可重建**（由日志折叠重算）或位图/区间压缩；它们是本轮新定位到的 `set` 增长源（§2.2）。

### 4.3 与已flush前缀 / T262 / T276 的关系（**【建议】**）

- **复用 T262**：段文件就是"周期 flush 的产物"；分段=把 flush 从"防丢"升级为"**常驻上限**"。
- **T276 续跑**：续跑=读"最后一段 + 轻索引"重建内存视图；**`_observed_seqs_` 可从日志重建**（这正是 T272 指出的"不可重建→续跑重观测"的病根）→ **本方案顺带解 T276**。

### 4.4 【事实】kernel-dev 可行性约束（只读取证 `9a9e8393`）——**必须满足的 3 个硬条件**

1. **tail-only 后必须外置 `seq_base` 与 `chain_head`**：现状 `Arbiter.commit` 逐条 append，`Ledger.append` 用 `seq=len(self.records)`、`prev_hash=records[-1].hash`（`ledger.py:24-25`）→ 段释放后若不同步外置基准，**seq 会从 0 重来、哈希链断裂**。
2. **只能封"已 commit 的整回合"**：整回合回滚（ADR-08 `discard()`）依赖本回合缓冲可丢 → **禁止封 pending 缓冲**；建议在**回合 seal 之后、按 `SEG_ROUNDS` 对齐回合边界**封段（单线程 ⇒ 天然保全局全序）。
3. **索引与段必须同一原子替换**：复用 T262 temp+`os.replace`，**轻索引 offset 写在同一原子操作内**，否则崩溃时"索引↔段"不一致（半条问题从日志转移到索引）。

### 4.5 ⚠️ 【建议】kernel-dev 的**更优候选**：先做"增量聚合"（可能比"尾段常驻"收益更大、风险更小）

- **观察**：`state.event_index.values()` 的**全量扫历史 + 读 payload** 出现在多处（`scheduling.py:34,44` 读 `LLM_CALL`；`lifecycle.py` 读 `METABOLISM` series；`econ/exchange/production/liquidity/wake` 同理）——**它们本身就是 O(历史)/回合 的热点**（与 T254 同族）。
- **含义**：账本的痛**可能同时是"内存"与"计算"**。若"计算"才是真成本，则**"折叠时维护每类增量聚合（append-only 累加器）"比"尾段常驻"更优**（磁盘回读只会把 CPU 热点换成 I/O 热点）。
- **【待定】建议先 spike 量三项**：(a) 每回合 `event_index.values()` 扫描次数×长度；(b) 各类型读回频次；(c) N 曲线。**口径归 T8**。
- ⚠️ **scope 提醒**：若动这些折叠的**读法**，可能**越过"只改存储"的 scope** → 按 Leader 判据**必须显式标注 + 交用户知悉**（**不是说不能做**，是要标明）。

### 4.6 ★【事实】spike 已出（T285，`41c60d7` → `v2/refs/T285-event-index-spike.md`）——**选路已定：先增量聚合**

- **以"耗计算"为主**：N=10→20 时 `scan_len`/回合 **420,780 → 2,775,234（×6.6，近 O(N²)）**、墙钟 **4.0s→25.8s**；cProfile `dict.get` 占 30%，其余热点**全是 `event_index` 全表扫消费点**（`liquidity.recent_income` 7.5s / `econ._round_ie_eff` 3.9s / `visibility.visible_events` 8.2s / `location_of` / `recent_default_of` / `settlement.events_this_round`）。
- **常驻为次**：`event_index` N=20×24 ≈ **30.5MB（深尺寸估算 ±2×）**。
- **⇒ 修订推荐（本文 §4.5 的候选胜出）**：**① 首选"增量聚合"（消计算）→ ② 尾段常驻为次（消内存）；两路非互斥**。即 **T281 原命题（尾段常驻）降为"次项"**。
- **硬门禁（不可省）**：增量聚合须**证"增量表 == 全表扫"逐条等价**（不能假定）——同 T286 期①的"逐条逐字节对照"纪律。
- **【未验证】**：N=50 未测（需报备+内存上限）；O(N²) 外推未坐实。

## 5. 三项风险：可执行回答（**重点**）

### 5.1 可重建性

- **能**：`State = reduce(apply_event, 由段文件按 seq 顺序读回的事件, InitialState)`；**已封段 + 轻索引**即完整可重建。
- **与 `state_hash`**：`state_hash` 只依赖**折叠后的 state 投影**（不含 `event_index`/`records`）→ **分段/流式不改变 `state_hash`**（**前提：事件顺序与折叠语义不变**）。
- **与 TURN_SEAL**：seal 含 `last_seq/last_hash/money_*`，**不含全量 records** → 不受影响。
- **与 T276**：续跑读回窗口=「已封段 + 尾段」；**须保证"读回顺序 == 原提交顺序（seq 全序）"**（见 5.2）。

### 5.2 确定性 / 一致性（**scope 条件，非 D1**）

- **不改事件顺序**：段落盘与读回**必须按 `seq` 全局全序**；**禁止**并行乱序 append。
- **不改判定**：折叠器/验证顺序不变 → 判定不变。
- **不改 `state_hash`**：由 5.1 保证。
- **日志仍是唯一记录**（纪律①）：段文件 + 轻索引**必须能完整解释世界**（索引丢失可由段文件重建；段文件丢失=日志丢失，等同现状）。
- **消融可比**（纪律②）：`segment.enabled` 作为**独立开关**；同 sha 内只变它 → 可对照。

### 5.3 代价（**降内存换磁盘/时间**，量级）

| 维度 | 变化 | 量级（估计） |
|---|---|---|
| 内存 | **↓** 账本常驻从 O(全量) → **O(尾段)** | N=20×84 从 ~228MB → **~1/7（尾段 12/84）+ 轻索引**；N=50 收益更大 |
| 磁盘 | **↑** 段文件 = 现状 flush 产物（**T262 已有**），非新增量级 | 与现状日志同量（~57MB→~90MB@N=20） |
| 时间 | **↑** 历史事件读回（索引+段读取，可 LRU 缓存） | **【未验证】** 须实测：perceive/折叠 若频繁回读历史 → 可能变慢；**缓存命中率是关键** |
| 复杂度 | **↑** 落盘/读回/索引一致性、边界（段边界处） | 实现风险集中在"段边界 + 重放一致性" |

> ⚠️ **诚实**：**时间代价未实测**。若 `perceive`/统计大量回读历史，可能"省了内存、慢了长跑"。**必须先量"历史回读频次"**（`perceive` 是否真需要全历史——现状 `visible_events` 全量重扫**恰恰是 CPU 热点**，见 T254）→ 本方案与 T254 的**增量感知**天然协同。
