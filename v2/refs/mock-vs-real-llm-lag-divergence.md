# 纪律：mock 臂的 `lag` 分布不能用来代表真 LLM 臂

> 立件：Leader（team-leader）｜2026-10-29｜**补充** `v2/refs/D9-line-status-20261029.md`（`21ee33a0…`）§5 未闭合项
> 由来：`dialogue-core-dev` 三问核对时发现，两臂 `lag` 分布**形态显著不同**，而此前我只把"mock 不能代表真 LLM"用在了"语言/内容"维度上。

## 1. 事实（三臂，同口径）

`lag` = 子消息 `round` − 父消息 `round`；分母 = `reply_to` 非空的条数（= MSG 总数 − 发起数）。

| 臂 | MSG | 发起 | 回复（分母） | `lag` 分布 | `lag=2` 占比 |
|---|---|---|---|---|---|
| `mock_d9c_recent` | 929 | 266 | 663 | `{1: 656, 2: 7}` | **1.06%** |
| `mock_d9b_rw4`（对照） | 929 | 266 | 663 | `{1: 656, 2: 7}` | 1.06% |
| **真 LLM `d1_f6off`** | 686 | 206 | 480 | **`{1: 327, 2: 153}`** | **31.88%** |

⇒ 三臂 `lag=0` **全为 0**（一致），但 **`lag` 的形态差近 30 倍**（1.06% vs 31.88%）。

## 2. 纪律（写死）

1. **`lag` 分布属"行为形态"，不属"结构量"**。mock 能证明"某个开关是否改变了结构"（条数、线程数、turn 装配），但**不能**用来估计真 LLM 下回复的时间分布。
2. **凡以 `lag` 分布为读数的结论，必须在真 LLM 臂上复核**；只在 mock 上得到的 `lag` 数字，引用时必须标注「mock，不代表真 LLM」。
3. 反过来也成立：**D9c 的判定（`lag≥3 = 0`）在 mock 上成立，但不能推断真 LLM 臂也 `lag≥3 = 0`**——本批没有出现 ≥3，可能因为 mock 的行为空间比真 LLM 窄。**这是 D9c 判定的一处外部效度缺口，须与判定并列披露。**

## 3. 口径附注（避免同名不同义）

- `reply_to is None` **恰好等于发起**（mock 266、真臂 206），不是缺失或损坏；`None` 不计入任何"回复"分母。
- 两种口径同值：①`reply_to` 非空 = 663 / 480；②非空**且**能解析到父消息 = 663 / 480（**不可解析 = 0**，无悬空指针）。
- 异常检查：`reply_to` 非空但 `turn_index ∈ {0, None}` = **0**（三臂均 0，装配无异常）。
- 本件 `round` 一律取**台账事件的 `round` 字段**；`msg_id` 次末段口径见 R1 边界 13/14，两者不得混用。

## 4. 影响

- 本件**不修改** D9b / D9c 的任何判定与数字；
- 但引用 D9c 的 `lag` 读数时，必须同时写：**「mock 臂；真 LLM 臂的 `lag=2` 占比为其 30 倍，形态不可外推」**；
- 若将来要谈"真 LLM 下回复延迟"，必须新跑真 LLM 臂，不能拿 mock 数当估计。
