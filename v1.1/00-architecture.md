- **新增贯穿约束 C4**（生活层特有，与 T8 §0 一致）：凡「决策/检索/判定」类输出（计划、对话文本、记忆检索命中、反思生成、规范采纳与否）**一律以事件落日志**；统计与重放只折叠日志，**绝不重调 LLM、绝不重算嵌入**。

## 1. 三层架构：职责边界与数据流

### 1.1 分层总览（v1.1）

```
┌──────────────────────────────────────────────────────────────────────┐
│  L2  涌现观测层（Emergence Observation Layer, M8）— 只读、纯函数        │
│      metrics(log,T) = f(EventLog, turn_seal, TIME_CONFIG)             │
│      ├─ 确定性指标（判定用，无 LLM）  └─ LLM 描述层（可选，非权威）      │
└───────────────────────────────▲──────────────────────────────────────┘
                                 │ 只读（read-only）
┌───────────────────────────────┴──────────────────────────────────────┐
│  D0  确定性内核（Deterministic Kernel = 世界法则）                     │
│   Clock/Round Scheduler ──► 时间派生 round→slot→day→week              │
│   World State Store(+snapshot) ◄──► Central Rule Arbiter（唯一写入口） │
│   RNG Streams(层级化)   Ledger(append-only + SHA-256 哈希链)          │
│   Hooks: P0..P6；生活层挂 Phase 3.5（L1..L7）；经济/生命周期 4.1..4.8   │
└───────▲───────────────────────────────────────┬──────────────────────┘
        │ 感知 perceive()（只读视图）             │ 事件 events（唯一事实产出）
        │                                        │
┌───────┴───────────────────────────────────────▼──────────────────────┐
│  L1  人格生活层（Persona-Life Layer, M1/M2/M3/M4/M5/M7）— LLM + 记忆   │
│   感知世界 → T0/T1/T2 决策 → 产出（a）非货币状态（Phase 3.5 内结算）    │
│                            （b）货币/行为意图 → pending_intents → 4.x  │
│   内部：人格(M1)/记忆(M2)/关系(M3)/日程(M4)/场所昼夜(M5)/目标(M7)       │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.2 三层职责边界（【已定】）

| 层 | 定位 | **必须做** | **绝不越界** | 权威来源 |
|---|---|---|---|---|
| **D0 确定性内核** | 世界法则 | 时间派生、状态存储、裁决器全部 hook、账本、RNG、规则校验、全部货币/生命周期结算、所有判定 | 不做任何「内容生成」；不调用 LLM | v1 `03` + T8 `08` §2 |
| **L1 人格生活层** | Agent 的「生活与人格」 | 生成计划/对话/反思/记录等**内容**，产出**非货币状态**与**意图** | **不得直接写世界状态/账户**；不得绕过裁决器；不得自定货币后果 | T7 `07-life-layer.md` |
| **L2 涌现观测层** | 度量与描述 | 从日志**确定性重算**涌现/生活指标；LLM 仅做**描述** | **只读**，不写世界；判定不得用 LLM | T9 `07-emergence-observation.md` |

> **分层铁律**：**写世界的只有 D0 的中央裁决器（Arbiter）**。L1 产出的一切（包括 LLM 文本）在被 D0 封装为带完整 `payload` 的事件前，对世界状态**没有任何影响**。

### 1.3 数据流（一次回合的端到端）

```
① 感知   D0 ──perceive(agent)──► L1   （只读：可见事件、场所、自身 status、记忆引用）
② 决策   L1 内部 T0/T1/T2 生成内容与意图
③ 编排   L1 ──submit_intent──► Intent Queue（Phase 3 COMMUNICATE 之后）
④ 生活   D0 Phase 3.5 LIFE：L1..L7 结算「非货币状态」（场所/需求/关系/记忆/标签）
                       └─ 产出的货币后果 → state.pending_intents
⑤ 裁决   D0 Phase 4 ARBITRATE：4.1..4.8 统一校验并结算货币/生命周期意图
⑥ 记账   D0 Phase 6 COMMIT：追加 Event → Ledger（哈希链）+ 守恒校验 + 快照
⑦ 观测   L2 ──metrics(log,T)──► 指标快照（确定性）；LLM 描述（可选、非权威）
⑧ 干预   OBSERVER ──inject_seed_event──► D0（封装 SEED_EVENT，唯一的人类/观察者入口）
```

### 1.4 与 v1 架构的差异（一句话）

v1 = 「确定性内核 + LLM 决策外挂」（两层：内核 + 决策）。
v1.1 = 在 **不改变内核** 的前提下：**上移**出「人格生活层（内容与意图）」、**旁挂**出「涌现观测层（只读度量）」，内核**重新定位为世界法则 + 护栏 + 度量底座**。v1 的 hook 链 4.1–4.8 **顺序与语义冻结**，生活层以**新阶段 Phase 3.5** 挂载（T8 §2，【已定】）。

### 1.5 底座拆分：硬内核 / 软判定层 / 叙事层（用户约束，【已定】）

用户提出「把底座拆开：运行的确定性 与 事件判断/随机性 分离」。**方向采纳**，按修正版落为**三条职责带**——它与 §1.1 的**功能三轴并不矛盾**，而是对「LLM 到底被允许做什么」的**正交切分**：

| 角色带 | 执行者 | 允许做 | **绝对禁止** | 落在 §1.1 的哪一层 |
|---|---|---|---|---|
| **① 硬内核（Hard Kernel）** | 确定性代码 | 时钟、账本、结算、状态变更、**死亡判定** | **LLM 绝对不碰「金额 / 死亡 / 结算」三类数字** | D0 确定性内核 |
| **② 软判定层（Soft Judgment）** | LLM | **仅定性的社会判断**（如「这次师徒关系是否建立」「声望如何变化」） | 不产出任何**金额/死亡/结算**数字；判定结果**写入日志后冻结** | L1 人格生活层的「判定」子模块 |
| **③ 叙事层（Narrative）** | LLM | 把**已定结果**叙述成情节与对话 | **纯输出，不影响任何状态** | L1 人格生活层的「表达」子模块 |

**三条关键澄清（务必贯穿全篇，尤其 §5）**：

1. **随机性不得由 LLM 承担**。所有**分支 / 结果分布**由**种子化伪随机 RNG**决定（D-8）；LLM 只负责**往已定的随机分支里填充内容与情节**——**LLM 不是掷骰子的人**。
2. **LLM 判定结果冻结**。首跑允许调用 LLM 做定性判定；判定结果**写入日志后冻结**（`frozen=true`）。重放 / 统计**只读日志、不重问 LLM**，从而指标逐位可复现、可审计。
3. **可复现性口径**：首跑**可含** LLM 定性判定，但判定结果**冻结进日志**；`replay = reduce(apply, EventLog)`，**不重跑 LLM 判定** → **同日志逐位一致**。

> **与 §1.1 的关系**：功能轴 = 内核 / 生活层 / 观测层；角色轴 = 硬内核 / 软判定 / 叙事。二者**交叉**：硬核 = 内核的功能职责；软判定 + 叙事都**栖身于生活层内部**，是被**内核契约严格约束**的两个 LLM 子模块。观测层（L2）**不属于任何 LLM 角色带**（它只读日志、纯确定性）。
>
> **落地要点**：句子「LLM 只会润色情节」之所以成立，靠的是 **RNG 先定分支 → LLM 再填充** 的顺序。任何让 LLM 决定「是否发生 / 发生多少」的做法，都必须改造为「RNG 决定分布 → LLM 填充内容」（见 §5.4、§5.5，及冲突 AR-C8）。

## 2. 单小镇世界设定（「麻雀虽小五脏俱全」）

> 本节是 T7 人格生活层与 T8 `place` 枚举的**权威来源**。所有 `place_id` 为英文小写下划线名（与 v1/T8 命名规范一致）；中文名为展示名。

### 2.1 场景声明（【已定】）

- **单一小镇**，名为「**青溪镇（Qingxi Town）**」（展示名，可改）。
- **不引入跨场景/多世界维度**；`place` 为小镇内场所标识（T8 `08` §3.3 一致）。
- 小镇是**闭合经济系统**：生产→交易→消费→税收/再分配在镇内闭环。

### 2.3 小镇拓扑与移动（【已定】框架，取值可调）

- **中心–外围拓扑**：`plaza` 为**枢纽**，`market`/`cafe`/`park`/`town_hall` 环绕中心；`residence` 位于外围带；`farm`/`gate` 在最外围。
- **移动代价 `travel_ticks`（确定性）**：相邻场所 = 1 tick，跨一个环层 = 2 ticks，最远 = 3 ticks；`gate`↔中心 = 3。
- 移动以 `PLACE_MOVE` / `PLACE_ARRIVED` 事件落日志（T8 §1.2 A），`travel_ticks` 参与 `ACTIVITY_STARTED` 的 `start_tick` 计算。
- **待讨论 AR-D2**：是否引入**显式邻接矩阵 `TOPOLOGY`**（推荐：给出 17×17 常数矩阵落 config，保证可复现；默认按环层近似生成）。

## 3. 时间结构：回合–时段–日–周（先模拟周）

> **【已定】与 T8 `08` §3.1 完全一致**（T8 已按本文预留默认值落盘，这里正式确认并冻结参数）。

### 3.1 四层时间层级（【已定】）

```
回合 (round / tick)   引擎最小确定性节拍（Arbiter 每回合结算）
  └─ 时段 (slot)      1 时段 = 3 回合
       └─ 日 (day)    1 日 = 4 时段 = 12 回合
            └─ 周 (week)  1 周 = 7 日 = 84 回合
```

```python
TIME_CONFIG = {
  "ROUNDS_PER_SLOT": 3,          # 默认 3（可调 {1,2,3,6}，见 AR-D4）
  "SLOTS_PER_DAY": ["morning","afternoon","evening","night"],
  "DAYS_PER_WEEK": 7,
  "DAY_TYPES": ["workday"]*5 + ["weekend"]*2,   # 前 5 工作日 + 后 2 周末
}
# 派生（纯函数、无墙钟，T8 §3.1 derive_time）
#   rounds_per_day = 3*4 = 12 ; week = day // 7 ; slot_idx = (round % 12)//3
```

**换算速查（默认参数）**：

| 单位 | 回合数 | 备注 |
|---|---|---|
| 1 时段 | 3 | |
| 1 日 | 12 | 4 时段 |
| 1 周 | **84** | 7 日 |
| 4 周 | 336 | |
| 12 周 | 1008 | |

### 3.2 时段语义（【已定】框架，T7 细化活动模板）

| slot | 中文 | 生活语义 | 活跃场所 | 备注 |
|---|---|---|---|---|
| `morning` | 晨 | 起床、早餐、通勤、开工/开学 | `farm`/`workshop`/`school`/`office` | 周初含「周计划 PLAN」 |
| `afternoon` | 午 | 主要生产、交易、社交 | `market`/工作场所/`plaza` | `market` 撮合高峰 |
| `evening` | 暮 | 下班、社交、娱乐、家庭 | `cafe`/`hall`/`park`/`kitchen` | 大型活动/种子事件主场 |
| `night` | 夜 | 休息、睡眠、私密对话 | `residence`（多数场所关） | 低活动量 |

- **昼夜循环**：由 `slot` 直接承载；场所**营业时间表**为确定性常量（§2.2 列），夜段多数场所关闭 → 移动/活动意图被拒并记 `INTENT_REJECTED`。

### 3.3 周节律（【已定】框架，取值待 T7 标定 D7-3）

| 周内位置 | day_type | 行为倾向（`DAY_TYPE_PARAMS`） |
|---|---|---|
| day0 晨 | workday | **PLAN**：生成本周计划（Agentopia 式四相位之一） |
| day0–day4 | workday | 强制工作占比高、休闲权重低、大型社交事件概率低 |
| day5–day6 | weekend | 不强制工作、休闲权重高、大型社交事件概率高 |
| day6 暮/夜 | weekend | **REVIEW**：周回顾/反思 |

```
DAY_TYPE_PARAMS = {
  "workday": {"work_required": True,  "leisure_weight": 0.3, "social_event_prob": 0.05, "sleep_slots": ["night"]},
  "weekend": {"work_required": False, "leisure_weight": 0.7, "social_event_prob": 0.25, "sleep_slots": ["night"]},
}
```

> **关键不变量**：工作日/周末差异**只影响行为倾向与事件概率**，**不改变 tick 级经济/生命周期结算频率**（代谢、税、计息仍**每回合**发生，v1 契约不变，T8 X2/X3）。

### 3.4 「先模拟周」尺度的回合计数量级（【已定】）

- **最短可交付实验单元 = 1 个模拟周 = 84 回合**。
- **短窗基线**：1–2 周（84–168 回合）。
- **长窗**：4 周（336）→ 12 周（1008）。
- **关键可行性结论**：v1 曾判定默认参数下首个自然死亡约在第 **65 回合**才可能出现（v1 C-15/Q3）；**1 周 = 84 回合 > 65**，因此在「先模拟周」尺度下**死亡动态可观测**，无需额外延长窗口即可满足 H2 验证。
  - ⚠️ **约束 AR-D4**：若把 `ROUNDS_PER_SLOT` 降到 1（→ 1 周 = 28 回合 < 65），**周尺度内将观测不到自然死亡**，H2 失效。故 **默认 `ROUNDS_PER_SLOT ≥ 3`**；若需压缩成本改小，必须同时在 T10 设「死亡压力档」补偿。

### 3.5 时间审计锚点（【已定】）

- 跨时段/跨日/跨周时，Phase 3.5 L1 发 `TIME_MARK{round, week, day, slot, day_type}`（T8 §3.4）。
- **所有生活层事件必带**审计字段 `day / slot / day_type / place`（T8 §1.1），使按时段/日/周切片统计无需回算。

## 4. 层间接口契约（下游必须遵循）

> 本节是 T7/T8/T9 的**接口权威定义**。字段沿用 v1/T8 的 lower_snake_case 规范。事件**具体 schema 以 T8 `08` §1.2 为准**，本文定义**接口分类与调用契约**。

### 4.1 七条层间接口（IF-1 ～ IF-7）（【已定】）

| 编号 | 接口 | 方向 | 契约 |
|---|---|---|---|
| **IF-1** | `perceive(agent_id) -> WorldView` | D0 → L1 | **只读**：可见事件、场所状态、自身 status/余额、记忆引用。**无副作用**。 |
| **IF-2** | `submit_intent(agent_id, intent) -> ok\|rejected` | L1 → D0 | 唯一写入请求通道；**裁决器校验后**方可产生事实。 |
| **IF-3** | `emit(event)`（内核内部） | D0 → Ledger | 唯一事实产出；追加哈希链（v1 §6）。 |
| **IF-4** | `metrics(log, T) -> Snapshot` | Ledger → L2 | **只读纯函数**；不触发 LLM/嵌入（C3/C4）。 |
| **IF-5** | `inject_seed_event(seed) -> SEED_EVENT` | OBSERVER → D0 | 观察者唯一干预入口；经裁决器封装。 |
| **IF-2b** | `submit_judgment(agent_id, judgment_request) -> JUDGMENT_EVENT(frozen)` | 软判定层 → D0 | **软判定层唯一出口**：硬内核校验 `envelope`（合法选项/阈值/RNG 分支）后**冻结**为 `LLM_JUDGMENT` 事件（§5.5）。 |
| **IF-6** | `get_frozen_judgment(judgment_id) -> decision` | D0 → replay/stats | 重放/统计读**已冻结**判定，**绝不重问 LLM**（对应「LLM 判定结果冻结」）。 |
| **IF-7** | `narrate(fact_event_seqs) -> text` | 叙事层 → 侧存储 | **纯输出**：把已定事实叙述成情节/对话；记 `NARRATIVE` 事件（`affects_state=false`），**不改状态**。 |

### 4.4 观测层只读契约（IF-4）（【已定】）

- L2 **只能**读 `EventLog` 与 `turn_seal`；输入为 `(log, T, TIME_CONFIG)`，输出为**确定性快照**（T8 §4.0 命名空间）。
- **禁止**：调用 LLM、重算嵌入、读取 L1 私有内存、修改任何世界状态。
- **判定 vs 描述分离**：涌现/规范/关系的**判定**一律用确定性指标（T8 §4.1–4.10）；LLM 仅可生成**描述性文字**（散文/摘要），且**不得进入判定路径**（`llm_judged_metric_count == 0`，T8 §4.10）。

### 4.5 「不得绕过裁决器」的强制机制（【已定】）

1. L1 hook（L1–L7）**签名不返回货币 delta**，只返回**非货币状态** + `state.pending_intents`。
2. 所有货币后果统一由 4.1–4.8 校验结算；守恒校验（v1 §3.6/T8 新增不变量）会暴露任何「无事件记账」。
3. 生活层事件必须携带完整 `payload`（C4/X6），否则重放失败（硬报错）。
4. 统计/重放遇未知事件类型**立即报错**（T8 X4）。

### 4.6 软判定层 / 叙事层的接口契约（【已定】）

**软判定层（IF-2b → IF-6）——「先 RNG 定分支，LLM 再填充，最后冻结」**：

```
① 硬内核先算：eligibility（是否具备判定资格）+ 用种子化 RNG 抽出 branch envelope
   （可选集/阈值/概率区间等），发给软判定层。
② 软判定层（LLM）：在 envelope 内做**定性判断**（如 mentor_relation ∈ {formed, not_formed}）。
③ 硬内核封装并**冻结**：emit LLM_JUDGMENT{frozen=true}（§5.5），校验 decision ∈ envelope.options。
④ 硬内核据**冻结结果 + RNG** 确定性推导**数值后果**（如 RELATION_CHANGE 的 dim/delta），
   作为**独立确定性事件**落日志。
⑤ 重放：只读 ③ 的冻结判定（IF-6），**不重问 LLM**；④ 的数值后果已在日志中，直接折叠。
```

**叙事层（IF-7）——纯输出**：
- 输入是**已发生的事实事件**（`fact_event_seqs`），输出是情节/对话文本（入侧存储 + 哈希）。
- 记 `NARRATIVE{affects_state=false, body_ref, source_event_seqs[]}`；**不产生任何状态变更**；判定/统计**永不读叙事文本**。

> **边界**：软判定层的产物**绝不能**直接是金额/死亡/结算数字；它只给「定性标签」，数字一律由硬内核从标签 + RNG 确定性推导。

## 5. 确定性 / 非确定性边界（逐条）

> **总原则**：凡影响**世界状态、货币、生命周期、判定、复现**的，**必须确定性（代码）**；LLM 只负责**内容与意图**，且其产物**必须被封装为事件落日志**后方可影响世界。

### 5.1 必须确定性（D，代码、整数、无 LLM）（【已定】）

| # | 项目 | 说明 |
|---|---|---|
| D-1 | 时间派生 `round→slot→day→week` | 纯函数，无墙钟（§3.1） |
| D-2 | 阶段序列与 hook 顺序 | P0–P6；3.5 内部 L1–L7；4.1–4.8 冻结 |
| D-3 | 世界状态存储与快照 | |
| D-4 | 经济：撮合、清算、原子转账、手续费、税、UBI、铸币/销毁、计息 | v1 机制不变 |
| D-5 | 借贷准入（信贷规则）与坏账核销 | 非 LLM |
| D-6 | 生命周期状态机、判死/复活、安全阀 | v1 不变 |
| D-7 | 反作弊打标 `flags` 与 `I_eff/E_eff` | v1 不变 |
| D-8 | RNG 层级流 `(seed, stream_id, round, seq)` | SplitMix64，禁浮点 |
| D-9 | 场所合法性、容量、营业时段、`travel_ticks` | §2 |
| D-10 | 日程→slot 的**分配**（哪个 slot 执行）、活动资格 | |
| D-11 | 需求自然衰减/满足的**函数形式** | 值域与衰减系数确定 |
| D-12 | 关系维度的**数值更新函数与值域** `[W_MIN,W_MAX]` | LLM 不直接定数值（见 AR-C3） |
| D-13 | 记忆 **salience 规则**、反思**触发阈值**（累积重要性）、检索 top-k 结构 | 检索**命中结果落日志**，重放不算嵌入 |
| D-14 | 标签频次、规范采纳**阈值判定**（支持者 ≥ threshold） | 判定非 LLM |
| D-15 | 账本哈希链、`turn_seal`、重放 `fold(apply_event)` | 含 `LLM_JUDGMENT` 冻结读回（IF-6）；复现口径 = **同日志逐位一致**（§5.4） |
| D-16 | 全部统计指标与判定 | C3 |
| D-17 | LLM 成本闸门（`LLM_BUDGET` 降级 T2→T1→T0） | 可审计 |

### 5.2 交给 LLM（N，仅内容/意图）（【已定】）

| # | 项目 | 约束 |
|---|---|---|
| N-1 | 人格自由文本（背景/性格描述） | 人格**配置**离线编写/种子固定；在线不重生成 |
| N-2 | 日/周**计划内容**（做什么、和谁、去哪） | 仅作意图；slot 分配与经济后果由 D0 定 |
| N-3 | 对话/消息**正文** | 落 `MSG_*`，配额受 D0 硬约束 |
| N-4 | 活动结果**叙述** | 数值结果由确定性结算 |
| N-5 | **反思文本**、记忆**正文** | 触发与选点确定性；文本落侧存储+哈希 |
| N-6 | 关系**印象叙述** | 数值由 D-12 定，LLM 只写描述 |
| N-7 | **意图生成**（下单、转账、要约对象） | 经 IF-2 校验 |
| N-8 | 涌现**描述**（散文，非判定） | 不得进入判定路径 |

### 5.3 边界争议点（【待讨论】/【冲突】）

- **AR-C3【冲突】**：关系维度数值若由 LLM 直接给出，则关系图不可复现、T9 的图指标失效。**架构裁定：关系数值必须由确定性函数（D-12）从事件 cause 推出；LLM 只产叙述**。若 T7 设计为「LLM 定关系数值」，必须改为「LLM 建议 → 确定性函数夹取/量化」，否则违反 C3。
- **AR-C4【待讨论】**：记忆 `body` 是否入主日志（T8 XT-3）。架构建议：**入侧存储 + 哈希引用**，主日志只存 `body_ref/embed_ref`（可审计 + 瘦身）。
- **AR-C5【待讨论】**：嵌入模型版本是否冻结进 `engine_version`（T8 D7-6）。架构建议：**冻结**（否则同 seed 首跑不可复现）。

### 5.4 三条澄清（用户约束，【已定】——本节为边界判定的最高优先口径）

1. **随机性不由 LLM 承担**：所有分支 / 结果分布由**种子化伪随机 RNG**（D-8，`(global_seed, stream_id, round, seq)`）决定；LLM 只在**已定分支内填充内容与情节**。**LLM 不是掷骰子的人**。任何「LLM 决定是否发生 / 发生多少」的设计，必须改造为「RNG 决定分布 → LLM 填充内容」。
2. **LLM 判定结果冻结**：软判定层首跑可调用 LLM，判定结果**写入日志后冻结**（`LLM_JUDGMENT.frozen=true`）；重放 / 统计**只读日志、不重问 LLM**。
3. **可复现口径 = 「同日志逐位一致」，不是「同 seed 重跑一致」**：
   - ✅ 保证：`replay(log) = reduce(apply, EventLog)` 对**同一份日志**逐位一致；`metrics()` 对同日志两次调用字节相等。
   - ⚠️ **不保证**：首跑含 LLM 定性判定，故**跨跑（同 seed 重跑）不保证逐位一致**——这是**有意接受**的权衡（换取 LLM 定性判断能力）。
   - 该口径**取代** v1「同 seed 重跑逐位一致」的表述；v1 纯确定性部分（金额/死亡/结算）仍逐位确定，但整体实验的复现单位是**日志**。

> **对下游的影响**：T10 判据中的「可复现性」应以 **`replay(log)` 一致 + `metrics` 字节相等** 判定，而**不应**要求「同 seed 两次首跑状态哈希一致」（后者对含 LLM 判定的 v1.1 不成立）。

### 5.5 「LLM 判定结果冻结」数据结构（【已定】）

软判定层的输出**必须**由硬内核封装为如下结构并落日志（沿用 v1/T8 事件外壳）：

```python
class LLMJudgment:                      # Event.type == "LLM_JUDGMENT"
    # —— v1 事件外壳（沿用 T8 §1.1）——
    seq: int; round: int; phase: int    # phase = 2（DECIDE）
    actor: AgentId | "SYSTEM"
    mono_ts: int; prev_hash: str; hash: str
    # —— 软判定载荷 ——
    judgment_id: str                    # 全局唯一
    parties: list[AgentId]              # 相关主体（如 [a, b] 师徒双方）
    dimension: str                      # 判定维度，如 "mentor_relation" / "reputation"
    question_ref: str                   # 判定问题的规范标识（模板 id）
    envelope: dict                      # 硬内核预先给定的约束：options/threshold/rng_branch
    decision: str | int                 # ★ 冻结的定性判定结果（必须 ∈ envelope.options）
    context_digest: str                 # ★ 相关上下文摘要（规范 JSON 的哈希，供审计）
    context_ref: str                    # 上下文正文侧存储引用（可选）
    model: str                          # ★ 判定模型/版本
    prompt_hash: str                    # 规范 prompt 哈希
    created_round: int
    frozen: bool = True                 # ★ 冻结标记（恒 true）
    effect_ref: int | None              # 由该判定驱动的确定性数值事件的 seq
```

**重放 / 统计语义**：
- `apply_event(state, LLM_JUDGMENT)` → `state.judgments[judgment_id] = decision`，**不调用 LLM**。
- 数值后果（如 `RELATION_CHANGE`）是**由 `decision` + RNG 确定性推导的独立事件**，已在日志中，直接折叠。
- **成本/完整性审计**：`LLM_CALL`（成本）与 `LLM_JUDGMENT`（冻结判定）分列；判定必须有对应 `LLM_CALL`，否则记 `SYSTEM_ERROR`。

> **必带四要素**（用户约束）：**判定结果 `decision` + 判定模型/版本 `model` + 相关上下文摘要 `context_digest` + 冻结标记 `frozen=true`**，一并写入日志并冻结。

## 7. 可行性与成本量级（先模拟周）

### 7.1 计算/日志可行性（【已定】框架，量级待 T10 标定 D7-5）

沿用 T8 §5.1 模型，按「1 周 = 84 回合」：

每回合事件量 `E_round ≈ N×4.3 + M_msgs + E_sys`（`M_msgs≈0.6N`，`E_sys≈5`）：N=10→~60、**N=20→~100**、N=50→~250。

| 运行 | 回合 | **N=20（目标）** 事件量/体积（原始→压缩） | N=10（沙盒） | N=50（展望） |
|---|---|---|---|---|
| **1 周** | 84 | ~8.4e3 / ~2.5MB → ~0.6MB | ~5.0e3 / ~1.5MB → ~0.4MB | ~2.1e4 / ~6.3MB → ~1.6MB |
| 4 周 | 336 | ~3.4e4 / ~10MB → ~2.5MB | ~2.0e4 / ~6.0MB → ~1.5MB | ~8.4e4 / ~25MB → ~6.3MB |
| 12 周 | 1008 | ~1.0e5 / ~30MB → ~7.6MB | ~6.0e4 / ~18MB → ~4.5MB | ~2.5e5 / ~76MB → ~19MB |

**结论**：目标规模 N=20 下，即便 12 周压缩后日志仅 **~8MB** 量级；即便展望档 50 Agent × 12 周也仅 **~20MB**，**日志/复现不是瓶颈**；**唯一显著成本是 LLM 调用**。

### 7.2 LLM 成本量级（【已定】公式 + 默认值，系数待标定）

```
每 Agent 每周 LLM 调用 ≈ c_life·(SLOTS_PER_WEEK) + c_social·(SLOTS_PER_WEEK)
  SLOTS_PER_WEEK = 28
  c_life   = 每时段生活层调用（计划/活动/反思摊薄）  默认 1.0（0.5–3.0）
  c_social = 每时段社交/决策调用                     默认 0.5（0.2–1.5）
  → 每 Agent 每周 ≈ 42 次（T1 为主，T2 于关键事件）
```
| 规模 | 每周调用量级（估） | 每周 token 量级（估） | 说明 |
|---|---|---|---|
| N=10（沙盒起步） | ~4×10² | ~10⁶ | 短窗基线 |
| **N=20（目标，1 周）** | **~8×10²** | **~2×10⁶** | **主目标档**（跑通对象） |
| N=20（目标，4 周） | ~3.4×10³ | ~8×10⁶ | 中期窗口 |
| N=20（目标，12 周） | ~1×10⁴ | ~2.5×10⁷ | 长窗，须分批 |
| N=50（展望，1 周） | ~2×10³ | ~10⁷ | **达标后再评估放量** |

- **对照**：Agentopia 单世界一年 ≈ 13.7B token / 56.7 万次调用 / 186 小时。v1.1 目标档单周成本（~2×10⁶ token）**远低于**其年尺度，说明「先模拟周」在成本上**可行**。
- **成本闸门**：沿用 `LLM_BUDGET`，超限按优先级（濒死 > 投资/结盟 > 常规）降级 T2→T1→T0，写 `LLM_CALL(degraded=true)`。
- **【冲突 AR-C5】**：v1 的「≤8 次 LLM/回合」是为**纯经济沙盒**标定；生活层（计划/对话/反思）会显著抬高。T10/T8 **必须按新模块重算预算**，不可直接沿用 8。
